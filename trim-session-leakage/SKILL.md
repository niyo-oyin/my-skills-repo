# セッションの漏れを取り除く

セッションの漏れとは、リポジトリの視点ではなく、それを書いた作業セッションの視点で書かれた文章のことである。
そのセッションにしか見えなかった資料を引用する、状態ではなく変更を語る、すでにその場にいないレビュアーに反論する、といった形で現れる。

事実についての記述を含む文章は、削除するだけでは直らない。
それぞれの事実を、HEAD（リポジトリの現在のコミット）で書かれたとおりに成り立つ形に書き直してから、周囲の書き起こし（作業セッションでの思考をそのまま文章にしたもの）を削除する。
事実を含まない文章（監査項目の符号、処理手順の説明など）は、そのまま削除する。

このスキルは、`prose-contract` スキルの「命題をすべて残す」という規則を前提にしている。
これは指針であり、手順書ではない。
例は日本語だが、判定に使う問いは言語に依存しない。

## 判定に使う一つの問い

疑わしい箇所の一つひとつについて、次のように問う。

**HEAD を読む人は、作業セッションの記録、PR のスレッド、コミットされていない草稿を見なくても、すべての参照を解決し、すべての主張を確かめられるか。**

できないなら、残る事実をリポジトリの視点で書き直し、それ以外を削除する。
できるなら、どれほど経緯の話に見えても、漏れではない。

ただし、参照を解決できることで通るのは、この問いだけである。
現在の状態を説明する場所（README、ドキュメント、ドキュメントコメント）では、参照を解決できる変更の話も、変更の語りであることに変わりはない。
類型 3 に従って、経緯を書く場所に移す。

## 類型

1. **消えた設計セッションへの引用**：「（決定 7）」「（監査 C2）」「設計書 §4.7」「計画 §1.4」、フェーズのラベル（「フェーズ 2」「T4」）、「設計台帳」「（B 案の判断）」など。
  その決定を所有する、コミット済みの文書があれば、名前とパスで引用する。
  なければ引用を削除し、それが指していた事実を、単独で成り立つように書き直す。
2. **スタックと PR の視点**：「このスタックの後続の PR で」「この PR で追加する」「直前のコミットで」など。
  出荷された仕組みか、拡張点を書く。
  先送りした作業は、TODO の印か、issue への参照として記録する。
3. **変更の語りと版の刻印**：「以前は」「〜しなくなった」「旧実装」、および書いた時点に依存する刻印（「v1 では」「今回は」「現時点では」、過去と対比する「今は」）。
  現在の振る舞いを書く。
  修正済みのバグは、リポジトリの履歴（「以前は Y が起きていた」）としてではなく、現在形の反実仮想（「X がないと Y が起きる」）として書く。
4. **レビューのやり取り**：「レビューで却下」「レビュー済み」、草稿の版番号（「この文書の第 5 版で」）、どのラウンドで出た指摘かについてのメモ。
  残る決定と理由を、ただの事実として残す。
  誰がいつ言ったかは削除する。
5. **レビュアーに向けた正当化**：「このキャストは安全である。単に…だけだ」「…なので、これで正しい」。
  コードが妥当だと主張するコメントは、保守する人ではなくレビュアーに向けて書かれている。
  コードを安全にしている不変条件を書く。
  コードを見れば分かるなら、コメントを削除する。
6. **言い直しと処理手順の説明**：処理手順の説明（「まず X をして、次に Y をする」）、テストを順に追う説明、自明な分岐の証明。
  これらは削除する。
  自明でない契約と不変条件だけを残す。
7. **ぼかした表現と計画の名残**：「とりあえず、たぶん問題ない」「これで足りるはずだ」、印のない先送り。
  `TODO` か `FIXME` に格上げするか、実際の上限として書き直す。
  ぼかした言い回しは削除する。
8. **作業言語の名残**：一つの言語で書くことになっている場所に紛れ込んだ、別の言語の断片と作業用の区切り線。
  たとえば、英語で書く決まりのコメントに残った、日本語の作業メモである（「側」「設計メモ」「---- ここから非公開 ----」）。
  翻訳するか、削除する。

## 漏れではないもの

問いを使わずに引用を刈り込むと、両方の向きで誤る。
長く有効な参照を削除し、消えた参照を残してしまう。
次の「残す規則」を、書かれているとおりに適用する。
それぞれについて判断の実例が[例](references/examples.md)にある。

- **issue への参照**：`#1470`、`TODO(name):`、「後続の対応は issue #N が扱う」は、HEAD で解決できる。
  README を含め、どの場所でも残す。
  決定記録に移すこともしない。
- **経緯を書く場所の中の記述**：コミットメッセージ、PR、変更履歴、決定記録、ポストモーテムは、変更の経緯を書く場所である。
  そこでのマージ済みの PR や issue の引用は、認められた証拠である。
  経緯を述べる節の中では、過去の段階の名前（「最初の版では X を出荷した」）も認められる。
  ただし、書いた時点に依存する刻印（「今回は」）は、どこでも禁止である。
- **抑制の理由**：`eslint-disable … -- 理由` の理由、カバレッジ除外の理由、空の `catch` の説明は、必須の文章である。
  理由が間違っていれば、直す。
  決して削除しない。
- **現在形の反実仮想として書かれた退行防止の記述**：「X がないと Y が起きる」「単純に X すると…」。
- **実測に基づく上限**：定数を調整した根拠を示す「（実測：512 段の入れ子で約 0.15 秒）」。
  「実測」という語が、根拠を示す役割を担っている。
- **実行時の新旧**：「古い接続は、新しい接続が受け付けを始める前に、処理中のリクエストを最後まで処理する」は、実行時のライフサイクルであり、変更の経緯ではない。
- **リポジトリの外で解決できる参照**：規格の節（RFC 9110 §10.1.5）、デザインツールのフレーム名など。
  § の禁止が対象にしているのは、コミットされていない内部の草稿である。
  外部の規格と、節番号を自分で管理しているコミット済みの文書は、節で引用してよい。
- **プロジェクトとしての語り口と文書の種類に固有の形式**：プロジェクトを主語にした「私たち」と、決定記録の「検討した代替案」の節。

## ワークフロー

1. スコープと除外は、`prose-contract` に従う。
  スコープが明示されていなければ、尋ねる。
  ベンダリングされたサードパーティのコードと、凍結された記録には、決して手を入れない。
  記録されたフィクスチャとスナップショットは派生物であり、直す対象の文章ではない。
  それらを変更するのは、許可された振る舞いの変更に新しい証拠が必要な場合だけであり、その場合も、所有するソースかシナリオを直して再生成する。
2. まず、読み取り専用で監査する。
  [検索パターン](references/search-patterns.md)を実行する。
  どのパターンの出力も、信用する前に、既知の漏れの例に一致し、紛らわしいが漏れではない例に一致しないことを確かめる。
  そのうえで、ヒットを一件ずつ、意味で判断する。
  検索パターンは探りを入れるためのものであり、漏れの定義ではない。
  パターンにかからない漏れが必ずあるので、スコープの中で文章の密度が高い場所（モジュールのドキュメントコメント、README、決定記録）は、パターンを使わずに読む。
3. 場所ごとに、所有者から先に直す。
  生成されたカタログについては、利用側をすべてたどり、元のドキュメントコメントか生成器のテンプレートを直してから、派生物をすべて再生成する。
  モデルやユーザーに見える文言は、`prose-contract` に従い、その振る舞いを固定している証拠（テストやスナップショット）と一緒にだけ変更する。
  それができなければ、変更せずに、見送りとして報告する。
4. 何かを削除する前に、その箇所の命題を列挙し、その変更が[直しすぎの罠](references/examples.md#直しすぎの罠)のどれにも当たらないことを確認する。
  罠は次の四つである。
  義務を容認に変えること、仮定の話を出荷済みの機能として扱うこと、事実を周囲の文章ごと削除すること、根拠の出どころを省くことである。
5. 検証する。
  検索パターンを再実行し、残っているヒットが、認められた「残すもの」と、このスキル自身のファイルだけであることを確認する。
  残っている引用がすべて HEAD で解決できることを確認する。
  変更した場所に対応する、プロジェクトのチェックを実行する。
