# 例：漏れとその直し方

これらの例は、文章のひな形としてではなく、それぞれの判断の背後にある原則を見分けるために使う。
このファイルは、判定の基準を確かめる材料として、漏れた言い回しを意図的に引用している。
ここにある言い回しを、ほかの場所で使ってよいわけではない。

## 消えた引用

### 所有する文書がある決定番号

**漏れ：** 「スラッシュ入力は、表示中のカタログに対して解決する（決定 21）。」

**修正：** 「スラッシュ入力は、表示中のカタログに対して解決する。これはプレーンテキスト参照の決定であり、`docs/decisions/input-pipeline.md` が所有する。」

この番号は、HEAD のどこを探しても解決できない。
決定の名前と、それを所有する文書のパスなら解決できる。
所有する文書のパスは、ファイルごとに少なくとも 1 回示す。
リンクを書ける場所では、リンクにする。
2 回目以降は、検索できる名前だけでもよい。

### 所有する文書がない決定番号

**漏れ：** 「レジストリは、重複した名前を拒否する（決定 7：名前は平坦で、名前空間はない）。」

**修正：** 「レジストリは、重複した名前を拒否する。名前は平坦で、名前空間はない。」

「決定 7」を所有するコミット済みの文書はないので、引用は削除する。
しかし、引用が運んでいた事実（名前は平坦である）は一緒に削除せず、単独で成り立つように書き直す。

### 監査の略号

**漏れ：** 「描画は純粋である。同じスナップショットからは、同じ文字列が得られる（監査 R3）。」

**修正：** 「描画は純粋である。同じスナップショットからは、同じ文字列が得られる。」

リポジトリに監査の文書はない。
この略号は作業メモであり、命題を何も含んでいない。

### コミットされていない草稿の節番号

**漏れ：** 「レイヤー構成は、設計書（v2 §3.2）に従う。`src/core/` は純粋なコアである。」

**修正：** 「レイヤー構成：`src/core/` は純粋なコアである。」

誰もコミットしなかった草稿の `§N` は、解決できない。
これに対して、「RFC 9110 §10.1.5 に従ってエスケープする」は残す。
外部の規格は、もともとリポジトリの外で解決するものである。
節番号を自分で管理しているコミット済みの文書も、節で引用してよい。

### 計画のフェーズのラベル

**漏れ：** 「`src/client/` はシェルである（フェーズ 4）。アダプターは、移行フェーズ 1 が担当する。」

**修正：** 「`src/client/` はシェルである。アダプターは `src/client/adapters/` にある。」

フェーズのラベルが指している計画は、リポジトリに入らなかった。
それぞれのラベルを、そのフェーズが作ったものに置き換える。

## スタックと PR の視点

### 長く残る文章の中のスタック上の位置

**漏れ：** 「将来のリモートバックエンドは、このインターフェースを実装する（サンドボックスのバックエンドは、このスタックの後続の PR で入る）。」

**修正：** 「リモートバックエンドは、描画層を変更せずに、このインターフェースを実装できる。」

長く残る文章からは、スタックが見えない。
拡張点の契約を残す。
未着手の作業を書く場所は、PR そのもの、`TODO`、issue のいずれかである。

### README の中の「この PR」

**漏れ：** 「この PR で、セッション一覧にカーソルによるページ分割を追加する。」

**修正：** 「セッション一覧はカーソルでページ分割する。」

README は、どの PR よりも長く残る。
仕組みを、現在の事実として書く。

## 変更の語りと版の刻印

### PR 番号付きの苦労話

**漏れ：** 「以前は、色を `--widget-*` トークンから取っていた。しかし、このトークンを定義している箇所がなかったので、常にフォールバックで描画されていた。エイリアストークンによって、これを修正した（PR #88）。」

**修正：** 「色はエイリアストークンから取る。未定義のトークンはフォールバックで描画される。」

生きている事実は二つあり、どちらも残っている。
現在の仕組みと、今も成り立つ失敗時の振る舞いである。
どちらも、現在形で書き直してある。
バグの来歴は、PR と決定記録に書くものである。

### 削除の語り

**漏れ：** 「`probe` フィールドは、今回の整理で削除した。バッジは、今は汎用の射影ペアに乗っている。」

**修正：** 「バッジは汎用の射影ペアを使う。」

`probe` を見たことのない読み手は、それがなくなったと言われても、何も得られない。
削除された過去と対比する「今は」は、版の刻印である。

### 修正済みのバグを現在形の反実仮想にする

**漏れ：** 「以前は、マルチバイトのラベルが二重にエンコードされていた。」

**修正：** 「バイト長のガードがないと、マルチバイトのラベルは二重にエンコードされる。」

退行を防ぐための記述は、ガードを名指しする現在形の反実仮想として残る。
「以前は」と書くと、リポジトリの履歴を掘り返さなければ確かめられない記述になる。

### 書いた時点に依存する版の刻印

**漏れ：** 「今回は、バッチ描画を同期で行う。非同期の経路は、ロードマップ上の作業である。」

**修正：** 「バッチ描画は同期で行う。」
作業を先送りしているなら、呼び出し箇所の `TODO(widget-batch):` に記録する。

「今回は」「v1 では」「現時点では」は、マージされた瞬間に古くなる。
決定記録の経緯の節にある過去の段階の名前（「最初の版では X を出荷した」）は、いつ読んでも成り立つ。
書いた時点に依存する言い回しは、どこに書いても成り立たない。

## レビューのやり取り

### 文章になったレビューの判定

**漏れ：** 「レビューで却下：解決済みの仕様のキャッシュ。解決は、呼び出しごとに行う。」

**修正（決定記録の「検討した代替案」の節で）：** 「**解決済みの仕様をキャッシュする。** 却下。仕様は呼び出しごとの作業ディレクトリに依存するので、リクエストをキーにしたキャッシュでは、古いルートが返される。」

「検討した代替案」という形式が、認められた置き場所である。
誰がその点を指摘したかという経緯は、理由の一部ではない。

### 草稿の版番号

**漏れ：** 「この文書の第 5 版から、ローダーはマニフェストも検証する。」

**修正：** 「ローダーはマニフェストを検証する。」

実装済みの決定記録は、出荷された現実を述べる。
文書そのものの改訂の履歴は、git にある。

## レビュアーに向けた正当化

### キャストの弁護

**漏れ：** 「このキャストは安全である。オブジェクトを構築したのは SDK であり、単に任意フィールドの宣言が十分に厳密でないだけだ。」

**修正：** 「SDK は、任意フィールドをすべて埋めた状態で、このオブジェクトを構築する。宣言された型は、実行時の保証より緩い。」

保守する人が壊してはならない不変条件を書く。
「単に…だけだ」は、HEAD では誰も出していない異論に答える言い方である。
不変条件がコードから分かるなら、書き直さずにコメントを削除する。

### レビューを正しさの根拠にしない

**漏れ：** 「ラップの順序はレビュアーが確認したので、これで正しい。」

**修正：** 削除する。
ラップの順序は、関数の `@returns` に書かれている。

正しさの主張が引用するのは不変条件かテストであり、人ではない。

## 言い直しと導出

### 制御フローの語り

**漏れ：** 「まずラベルを正規化し、次に切り詰め、最後に折り返す。」

**修正：** 削除する。

コメントの下の 3 行が、同じことをコードで述べている。

### テストを順に追う説明

**漏れ：** 「このテストは、セッションを作り、メッセージを 2 通送り、2 通目の返信を待ってから、ログが 4 件であることをアサートする。」

**修正：** 「2 往復で、ログはちょうど 4 件になる。射影が、共有される接頭部分の重複を取り除くためである。」

アサートしている内容の背後にある、自明でない理由だけを残す。
順に追う説明は、テストの本体を言い直しているだけである。

## ぼかした表現と計画の名残

### 印のない先送り

**漏れ：** 「とりあえず、先に描画してしまっても、たぶん問題ない。」

**修正：** 削除する。
この先送りには、すでに `TODO(widget-batch):` の印がある。

所有者のいないぼかした表現は、計画の名残である。
印がなければ、ぼかした表現を残すのではなく、印を書く（`TODO(name): アニメーションフレームごとにまとめる`）。

### あいまいな大きさの見積もり

**漏れ：** 「バッファは 64 KiB あれば、ほとんどの場合は足りるはずだ。」

**修正：** 「64 KiB は、観測された最大のフレーム（48 KiB）に余裕を持たせた値である。これより大きいフレームは、`decode` で明示的に失敗する。」

ぼかした表現を、実際の上限と、それを超えたときの失敗の振る舞いに置き換える。

## 作業言語の名残

**漏れ：** "The renderer runs on the client 側; see the 設計メモ for spacing. ---- ここから非公開 ----"

**修正：** "The renderer runs on the client side; spacing follows the Figma frame `widget-badges`."

作業言語の断片と作業用の区切り線は、書き写したときの名残である。
Figma のフレーム名は残す。
これは、もともとリポジトリの外で解決する外部の出典である。

## 振る舞いとして見える文言

**疑わしい箇所：** エクスポートされたドキュメントコメントに「当面は利用できる」とあり、生成器がその文を、モデルに見えるカタログにコピーしている。

**誤り：** 文章だけを対象にした一括の修正の中で、元の文だけを書き換える。
または、生成されたカタログだけを手で編集する。

**正解：** 元の文がコピーされている先をすべてたどり、所有者を直し、派生物をすべて再生成し、その文言を固定しているテストとスナップショットを更新する。
画面に表示される文言については、プロジェクトが求める振る舞いの証拠も含める。
許可されたスコープにその文言を固定するシナリオがなければ、変更せずに、見送りとして報告する。

## 残すもの

### issue への参照はどの場所でも長く有効である

**残す：** 「上限は、ラッパーを含む描画後の値全体に適用する（後続の対応は issue #1470 が扱う）。」

問いを使わずに作業すると、「issue の引用は決定記録に書くものだ」と考えて、これを削除しがちである。
それは向きが逆である。
issue は、どの場所からでも HEAD で解決できる。
「後続の対応は issue #N が扱う」は、README で先送りした作業を示す、認められた書き方である。
決定記録やポストモーテムのような経緯を書く場所で追加で認められるのは、マージ済みの PR を証拠として引用することである。

### 消えた名前を挙げても所有者を示したことにはならない

**削除する：** 「ウィジェットの継ぎ目の上に載るバッジレンダラー（ウィジェット描画の RFC を参照）。」

問いを使わずに作業すると、「所有する文書を主題で名指ししている」と考えて、これを残しがちである。
判定の基準は、形ではなく、解決できるかどうかである。
「ウィジェット描画の RFC」に当たるコミット済みのファイルはないので、この参照は消えている。
コミット済みの所有者があれば、参照をそこに向け直す。
なければ、削除する。

### 抑制の理由

**残す（直したうえで）：** `// eslint-disable-next-line no-non-null-assertion -- 要素が 1 つのリテラルなので、添字 0 は必ず存在する。`

理由を述べる部分は、必須の文章である。
書かれている理由が事実と違う場合（たとえば、ループがどこにもないのに「上のループのガードによって、フレームの存在が保証される」と書いてある場合）は、理由を直す。
決して削除しない。

### 実測に基づく上限

**残す：** 「深さの上限（実測：512 段の入れ子で同期処理が約 0.15 秒、4096 段ではイベントループが止まる）。」

計測値があることで、根拠を知らない人が定数を調整し直すのを防げる。
「実測」という語によって、これが推測ではなくデータであることが分かる。

### 実行時の新旧は変更の経緯ではない

**残す：** 「古い接続は、新しい接続が受け付けを始める前に、処理中のリクエストを最後まで処理する。」

ここでの「古い」「新しい」は、引き継ぎの間、同時に生きている二つの実行時のオブジェクトを指している。
リポジトリの状態を指しているのではない。
変更の語りの禁止が対象にしているのは、リポジトリの履歴であり、ライフサイクルの用語ではない。

### 実行時の時刻は版の刻印ではない

**残す：** 「今日の日付は？」

このプロンプトは、実行時の時計について尋ねている。
「今日」は、リポジトリの状態どうしを対比していない。
ただし、この文面はモデルに届くので、書き換えるには、その振る舞いを固定する証拠が必要である。

## 直しすぎの罠

ここに挙げるのは、どれも実際の一括の修正で起きた誤りである。
ある箇所を削る前に、その命題を列挙する。

### 義務を容認に変える

**元の文：** 「これらの直接登録は、スロットへの移行を待っている例外である。」

**直しすぎ：** 「これらの直接登録は、認められた例外である。」

**正解：** 「これらの直接登録は、スロットへの移行を待っている例外である。」

「移行を待っている」は義務である。
「認められた」は、現状を是認している。
文を短くする過程で、モダリティ（義務か容認か）が逆になった。

### 仮定の話を出荷済みの機能として扱う

**元の文：** 「将来の IPC ベースのシェルは、エグゼキューターを継承して `spawn` をオーバーライドする。」

**直しすぎ：** 「IPC ベースのシェルは、エグゼキューターを継承して `spawn` をオーバーライドする。」

**正解：** 「仮に IPC ベースのシェルを作るなら、エグゼキューターを継承して `spawn` をオーバーライドすることになる。そのようなシェルは存在しない。」

「将来の」を削除するだけでは、設計の説明が、そのクラスが出荷されているという主張に変わる。
将来を示す語を取り除くだけで済ませず、仮定であることを明示する。

### 事実を周囲の書き起こしごと削除する

**元の文：** 「エラー通知は、チェックの順序を一つずつ順に説明する。通知の文面は、ドキュメントの型チェックが照合する対象でもある。」

**直しすぎ：** 語りだとして、その箇所を丸ごと削除する。

**正解：** 「通知の文面は、ドキュメントの型チェックが照合する対象である。」

前半は語りだったが、後半は、別の仕組みが依存している事実だった。
一つの場所に複数の命題がある場合は、文の単位ではなく、命題の単位で削除する。

### 数値を残して計測値であることを省く

**元の文：** 「上限の 4 MiB は、実測に基づく。生成される型定義モジュールのうち、最大のものは 3.1 MiB である。」

**直しすぎ：** 「上限は 4 MiB である。生成される型定義モジュールのうち、最大のものは 3.1 MiB である。」

**正解：** 「実測」を残す。

「実測」がないと、3.1 MiB が、観測値ではなく定義として読める。
そうなると、上限を引き上げる前に、誰も計測し直さなくなる。
