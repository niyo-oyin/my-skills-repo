# 計測に基づく高速化

「速くしてほしい」という漠然とした依頼を、ユーザーが実際に通る経路での再現可能な計測と、証拠に裏付けられた小さな修正に変える。
これは指針であり、ノルマでも手順書でもない。広く調べたうえで、計測されたコストを追う必要がある。
魅力的に見えても、ユーザーが実際に実行するワークロードを改善しない変更は退ける。

## スコープと現在有効な根拠を確認する

`AGENTS.md` と `CLAUDE.md`、アーキテクチャのドキュメント、テストの方針、影響を受けるパッケージの指示と決定記録を読む。
プロセス、時計、ブラウザテスト、非同期の後始末については、`test-reliability` スキルを使う。

ユーザーに見える終点、ワークロードの範囲、リソースの制約、許容できる小さな振る舞いの違い、作業をどこで止めるかを、最初に合意しておく。
バックエンドの計測と、ブラウザを含むエンドツーエンドの計測は、はっきり分ける。
履歴の読み取りやクライアント側の畳み込み（fold）が速くても、転送、描画、スクロール、入力への応答が速いことの証明にはならない。
ローカルのオーバーヘッドを計測するときは、モデルとネットワークの遅延を除外する。
除外したことを明記し、その結果を製品全体の遅延と呼ばない。

ローカルのチェックアウトだけでなく、現在のベースブランチそのものを調べる。
最終的にマージされた差分、それを所有するソース、テスト、解決済みのレビュースレッドを読む。
PR の説明には、破棄された実装が書かれていることがある。
マージ済みの証拠、マージされずに閉じられた作業、置き換えられた作業、見積もり、新しく取った計測値を区別する。
過去の性能改善の記録は調査の手がかりであり、その実装を再び持ち込む根拠ではない。

## 性能改善の候補を利用者の経路ごとに順位づけする

スコープが広い場合は、独立した領域ごとに委任する。
推測ではなく、計測値と本番の呼び出し箇所を必ず求める。
調べる領域の例を次に挙げる。

- コールドスタート、初回の読み込み、開き直し、書き込み可能な状態での再開。
- 項目数の多い履歴、個々のデータが大きい履歴、子の一覧、項目間の移動の繰り返し。
- 初期データの転送と畳み込み、最初に操作できる描画、古いページの読み込み、スクロール、詳細の展開、非表示だったビューの有効化。
- 差分の更新と再接続。
  長時間の処理、ほかの処理との混在、確定、キャンセル、終了処理を含む。

独立したコスト要因を一つずつ変化させる。
バイト数、永続化されたイベント、レコード、差分、往復の回数、子の数、表示中の DOM ノードは、それぞれ別の量である。
小さな同一のメッセージを大量に並べたものを、どのユーザー操作に負荷をかけるのかを確かめずに「現実的」と呼ばない。
典型的なワークロードと、裾の重いワークロードの両方を含める。
ただし、判断の役に立たない網羅的な組み合わせの表は避ける。

候補は、観測されたユーザーの待ち時間、CPU とメモリ割り当て、保持されるメモリ、発生頻度、確信の度合いで順位づけする。
候補ごとに、本番でそれを使う箇所、繰り返されている処理、想定される計算量、反証可能な最小の介入、変えてはならない振る舞いを挙げる。
疑わしいループ、使われていないキャッシュ、大きなファイルがあるというだけでは、ボトルネックの証拠にならない。

## 合成ベンチマークを設計する

プロジェクトにベンチマークの基盤や性能ゲートがあれば、その規約に従う。
較正や報告のための基盤を別に作って競合させず、既存の必須チェックを拡張する。
パッケージ内に閉じた診断は、その所有者のそばに置く。
パッケージをまたぐ必須のケースは、それが計測するユーザーの経路の下に置く。

ユーザーがローカルのデータを調べることを許可した場合でも、取り出すのはワークロードの集計上の特徴だけにする。
プロンプト、出力、パス、人や組織の名前、ID、認証情報、記録、それと分かる断片を、フィクスチャ、ログ、スクリーンショット、PR、成果物に決してコピーしない。
固定の入力は、レビュー済みの定数から生成する。
ベンチマークを、ユーザーのホームディレクトリ、たまたま存在するリポジトリ、ネットワークサービス、非公開のデータに依存させない。

実装の前に、計測カードを記録する。

| 項目 | 決めておくこと |
|---|---|
| ユーザーの操作 | 正確な操作と、外部から観測できる完了条件 |
| ワークロード | 固定する次元、分布、構築に使うシードや定数、それが通常の利用と裾の利用を再現できる理由 |
| 入口の経路 | 本番の呼び出しと構成、ビルド済みの成果物。モックにする外部の境界 |
| 時計 | 計測に含める準備、コールドかウォームか、計測の開始と終了、除外するコスト |
| メモリ | 終点で到達可能なオブジェクト、基準値、GC の扱い、保持分と一時分の上限 |
| 判定 | 生のサンプル、採用する集計値、較正した上限（絶対値、比率、メモリ）、陰性対照 |
| 振る舞い | それを所有する機能テストやスナップショット、許容する小さな違い |

ビルド済みの成果物を、出荷されるときと同じ方法で実行して計測する。
開発用ローダーのオーバーヘッドとモジュール解決は、出荷される経路ではない。
UI のケースでは、既存のテストハーネスを通して、ビルド済みの製品アセットを使う。
計測のためだけに、本番のエクスポートを追加しない。
アルゴリズムを「ベンチマーク用の実装」にコピーすることもしない。

コールドのサンプルとプロセスのメモリのサンプルには、新しい子プロセスと専用の一時ディレクトリを使う。
ウォームのサンプルでは、意図したキャッシュを明示的に保持する。
コールドであるはずのシナリオを、フィクスチャの準備が気づかないうちにウォームにしてしまうことがあってはならない。
比較の両側で、入力、検証、完了条件、到達可能な出力を同じにする。
解析して捨てるだけの基準値は、検証して保持する履歴と比較できない。

すべてのサンプルと、結果を決める集計値を報告する。
CI の時間の上限値には、既存の共有の時間較正と、レビュー済みのばらつきの余裕を使う。
バイト数、件数、無次元の比率を、CPU の速度に合わせて拡大縮小しない。
手動のブラウザ診断には、しきい値を設けない。
ブラウザの性能ケースを必須にするには、時間の上限値を採用する前に、明示的な決定と、実際の CI のブラウザとランナーでの繰り返しの計測が必要である。
別のランタイム向けに導出した補正係数だけでは、ブラウザの較正にならない。
上限値はソース内の定数とし、環境変数で上書きできるようにしない。
計測する処理は直列に実行し、自分が実行しているほかの CPU 負荷の高いジョブと重ならないようにする。
基準と候補は、比較できる条件で計測する。
退行を隠すために、上限値を広げたり、たまたま良かった実行を選んだりしない。

エンドツーエンドの遅延は、構成要素の各段階とは独立に計測する。
保持されるメモリは、意図したオブジェクトがまだ到達可能な状態で計測する。
一時的な負荷は、制約したヒープでの完走か、適切なピークの計測によって、別に計測する。
実行が速くなっても、保持されるメモリが際限なく増えるなら、無条件の改善とは言えない。

UI の応答性については、実際のブラウザ入力を使い、その結果として起きる UI の更新を観測する。
フレームと入力の計測には、最後の停滞も含める。
スケジュールされたタイマーと実際の入力を区別する。
合成イベントの生成には上限を設け、遅れを取り戻すための集中的な発生が別のワークロードを作り出さないようにする。
最初の描画、スクロール、ページ送り、差分の更新、有効化されたが非表示のビューのうち、どれを計測しているのかを明記する。
ブラウザなしで計測した畳み込み、偽の DOM、独自の周期イベントだけでは、ブラウザの応答性を立証できない。

## 退行を立証してから処理を減らす

本番のコードを変更する前に、最適化していない状態でワークロードを実行する。
コマンド、リビジョン、ランタイムとプラットフォーム、フィクスチャの次元、生の計測値、判定を保存する。
失敗するシナリオを縮小するのは、実際のボトルネックを通る範囲までにする。
そのうえで、修正を入れる前に、反証可能な仮説を順位づけする。
仮説を見分けるには、プロファイル、割り当てのサンプル、処理の回数、段階ごとの時間を使う。

次に挙げるのは、試す価値のあるよくあるパターンであり、機械的に適用する処方ではない。

- コンパクトな表現を、下流の読み取り側までコンパクトなまま保つ。
  利用側が必要とするのが確定した内容や一つの集計値であるなら、差分ごとのオブジェクトを作らない。
- 重複した解析、コピー、凍結、検証を取り除くのは、実際の所有者と、信頼境界を越える箇所を特定してからにする。
  同じプロセスの中で型の付いた値を借りているからといって、永続化されたデータや通信データの解析と検証を弱めてよいことにはならない。
- 成果物の変換は、すべての世代を保持するのではなく、ストリームで処理し、中間状態に上限を設ける。
  ユーザーの操作が必要とする箇所では、公開、検証、書き込み可能になるまでの準備の義務も含める。
- 読み取り専用の準備を、書き込みや公開の処理から分ける。
  ただし、完了を待つ必要のある処理を、正しさのために必要な終点より後ろに移さない。
- 非表示のビューと折りたたまれた詳細の処理を先送りする。
  最初の有効化と、保持される状態も計測する。
  先送りは削除ではなく、表示範囲だけをハイライトすることは完全な仮想化ではない。
- 同一性を安定させ、購読を絞って、一つのノードの変更で履歴全体が無効にならないようにする。
  更新の順序と、即時に配信されるイベントの振る舞いは保つ。
- 要素の移動、走査、再構築を繰り返す代わりに、適したデータ構造を使う。
  データ構造の操作だけを切り出して計測するのではなく、利用側の経路全体を計測する。
- リビジョンをキーにした再利用や、同時リクエストの集約は、明示的な無効化、保持量の上限、待機側ごとに独立したキャンセル、破棄の所有権がすべてそろっている場合にだけ使う。
  繰り返しのベンチマークを速く見せるためだけに、展開済みの表現をキャッシュしない。

一度に変える原因は一つだけにする。
絞り込んだシナリオと、それを含むエンドツーエンドのシナリオの両方を再実行する。
陰性対照を必ず求める。
厳しくしたアサーションが、元の実装か、対象のコストを意図的に戻した実装で失敗することを確認する。
退行が通ってしまうほど緩いしきい値は、保護にならない。
確認済みのノイズフロアを下回る上限値も、信頼できない。

## 振る舞いとリソースの所有権を保つ

性能の計測は機能面の証拠を補うものであり、その代わりにはならない。
出力、順序、ページ送り、ストリームの位置、エラー、キャンセル、並行性、破棄について、該当する範囲の狭いテストを実行するか追加する。
ユーザーやモデルに見える出力とログに記録される内容の同等性、公開されたデータの不変性、アトミックな公開、必要な検証、書き込み可能になるまでの準備を保つ。
数値を達成するために、履歴を黙って切り詰めたり、結果を飛ばしたり、ライフサイクルの意味を変えたりしない。

意図的に生じさせた、目に見える小さな違いは明記し、それを所有するテストかスナップショットで検証する。
機能面の期待値は、ベンチマークの内部に依存させない。
ベンチマークのアサーションに必要なのは、実際の終点に達したことを示せるだけの証拠であり、二つ目の機能テストスイートではない。

次のいずれかに当てはまる最適化は退ける。

- エンドツーエンドでは効果がなくなる。
- 典型的なワークロードが大きく退行する。
- 小さな効果に対して複雑さが大きすぎる。
- キャンセル、メモリの保持、永続性に関する振る舞いを説明もテストもできない。

退けた仮説は、それを正当化するためにスコープを広げることはせず、簡潔に記録する。

## レビューできる成果物にまとめる

長く残す根拠、代替案、較正、除外事項、残るリスクは、プロジェクトの決定記録の規約に従って書く。
関係する記録が置き換えの対象になるかを確認するが、性能改善の作業を、すべての記録の文章を整理する作業にしない。
再利用できる手順はこのスキルに置き、シナリオ固有の条件と数値は、そのベンチマークやパッケージの所有者のところに置く。

スタックされた PR を求められた場合は、編集する前に層を決める。
それぞれの層を、単独でマージできる状態に保つ。
ベンチマーク基盤の層は、計測した基準値を保護できる。
最適化の層には、その修正、機能テスト、より厳しい上限値を含める。
独立したボトルネックには、別々の PR スタックを使ってよい。
指摘への修正は、その変更を所有する層で行ってから、後ろの層に反映する。

プロジェクトのチェックを実行し、実際に実行して得た証拠だけを報告する。
ローカルの計測時間がランナー上での安定性を証明すると決めつけず、CI を確認する。
レビューの指摘は、コードと実行可能な証拠に照らして評価する。
理由か修正を返信し、対応したスレッドを解決済みにする。
ボットからの報告だというだけの理由で退けない。

結果はそれぞれ、ワークロード、変更前後の絶対値と比率、終点とメモリの意味、振る舞いの証拠、陰性対照、実行したチェック、除外事項の順に報告する。
作者が報告した過去の数値、新しく取ったローカルの計測値、CI の証拠を区別する。
合意したシナリオと修正の範囲で止める。
無関係な改善の機会を追わず、順位を付けた短いフォローアップの一覧を残す。
