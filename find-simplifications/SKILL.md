# 簡素化の候補を見つける

保守し続けている義務そのもの（API、データ表現、ライフサイクルの状態、設定の経路、依存関係、テスト、ドキュメント）をなくす変更を見つける。
削除の件数を増やすことより、根拠の確かな少数の候補を優先する。
これは指針であり、チェックリストではない。
ユーザーが指定したスコープを守る。
調査の依頼と、その提案を実装する許可は別のものである。

## スコープと制約を確認する

判断を始める前に、`AGENTS.md` や `CLAUDE.md` などのファイル、アーキテクチャのドキュメント、テストの方針を読む。
意図的な設計判断は、現在有効な決定記録で確認する。
アーカイブ済みの記録は過去の事例であり、現在の根拠にはならない。

まず、意図的に残されている設計を特定する。
たとえば、あえて重複させてある実装や、自前の実装が一つしかなくても外部の実装のために残してある拡張点がこれに当たる。
ユーザーがその制約を明示的に外さない限り、これらの削除を提案しない。
保護されている設計の中にある未使用のメンバーは、削除しても設計の目的が保たれるなら候補になる。

範囲の広い依頼では、独立した領域をサブエージェントに分担させる。
それぞれに範囲を区切った領域を渡し、利用箇所の証拠と、検討して退けた代替案を報告させる。
未使用のシンボルのような分かりやすいものだけでなく、本番で動いている大きな仕組みも調べる。
有望な削除が一つ見つかったところで調査をやめない。

## 取り除ける義務を特定する

次の問いを手がかりにして探す。
調査対象のコードが定めている要件、チェック、決定記録は、これから評価する設計上の選択そのものであり、その区別が必要であることを示す独立した証拠ではない。
候補について判断の基準を確かめたいときは、[判断のパターン](references/patterns.md)の該当する節を読む。

- **宣言された機能に入口から出口まで実際に効果を持つ経路があるか。**
  値の生成元、途中の変換、プロバイダーやエンドポイントでの処理、観測できる結果まで、端から端までたどる。
  あちこちにコピーされているフィールドでも、設定する箇所がない、読む箇所がない、拒否する実装しかない、ということがある。
  CLI や設定の値をそのまま渡している箇所では、最終的に優先される読み取りの経路をたどり、渡された値のうち、使われる前に別の値で隠されるものを見つける。
  呼び出し元だけでなく、コンストラクターと、判別子（discriminant）を出力する箇所も検索する。
- **どの区別が利用側の行動を変えるか。**
  まず、その区別、フィールド、アダプターがそもそも必要かを問う。
  トランスポート固有の印を新しく足す前に、既存のフィールドと判別子を、出力する箇所から認可と機能（capability）のチェックまでたどる。
  大まかな分類が、元のフィールドと同じ意味を持つとは限らない。
  区別を削除することと、その宣言を別の場所に移すことは分けて検討し、それぞれの案がどの入力や機能を受け入れるかを明記する。
  内部に状態がいくつあっても、ユーザーに見せる必要があるのは一つの状態や、使える一つの識別子だけ、ということがある。
  必要な認可、データの所在、永続性、所有権に関する振る舞いは保つ。
  使えない選択肢を増やすだけの公開上の区別は取り除く。
- **より小さな明示的な振る舞いに替えればサブシステムごとなくせないか。**
  固定の間隔、呼び出し側が渡すタイムゾーン、有効化の失敗を報告するだけの処理に替えると、汎用のカレンダー、永続化された既定値、自動ロールバックをなくせることがある。
  失う機能と、削除する仕組みを具体的に挙げる。
  本番の呼び出し元がある場合は製品の振る舞いについての判断になるが、それだけでは退ける理由にならない。
  実装は、ユーザーが許可した範囲にとどめる。
- **利用側は必要なときに正となる値を直接読めないか。**
  コピーされた履歴、昇格の状態を記録する台帳、無効化イベントの直後に行う読み取り、共有の配信ストリームの横に置かれた機能ごとのキャッシュを探す。
  その場で導出するか、すでにあるものを再利用すれば、購読、保持しているデータ、古い応答の処理、復旧の経路をまとめて削除できることがある。
  先に、いつの時点の値を観測する必要があるのかを確定させる。
- **構成が方針と取り違えられていないか。**
  任意のサービス、プロバイダーのメソッド、同列のツールが存在するかどうかは、機能が使えるかどうかを表せるが、デプロイ時の振る舞いの方針を決めるものではない。
  明示的な設定や、呼び出し側の意図を表す操作にすれば、レジストリや依存関係のチェックをなくせることがある。
  所有権や完了のタイミングが異なる操作は、分けたままにする。
- **保守コストの全体を誰が負担しているか。**
  重複したアプリケーションのツリー、製品が実際に使っているデモ用のランチャー、依存関係の解決のためだけにあるワークスペース、独自のアップグレード手順を持つインストール用のヘルパーをたどる。
  必要な振る舞いについては、生成側と利用側がすでに持っている拡張点を使う場合と、離れた場所にあるコアや共有の型宣言を変更する場合を比べる。
  削除する仕組みの全体と、置き換える仕組みの全体を、残るつなぎのコードも含めて比べる。
  不要な概念を所有者の近くに移しても、重複した定義を同期させるチェックを足しても、保守コストそのものはなくならない。

## 到達可能性とトレードオフを立証する

検索から始め、一致した箇所を読む。
正確なシンボル名、プロパティの読み書き、判別子、イベントや通信上の文字列、設定キー、パッケージ名、`.method(` と `method(` の両方の形を検索する。
テストと宣言は契約を示すが、出荷されるコードに実際の生成側や利用側があることの証明にはならない。

ソース、アプリケーション、実行時のスクリプト、出荷される設定とプロファイル、パッケージのマニフェストと公開エントリーポイント、ローダーによる解決、生成される実行時アセット、インストール済みパッケージの利用側を、調査の範囲に含める。
例とフィクスチャは、ディレクトリ名ではなく実際のエントリーポイントで分類する。
生成されたカタログは、その利用側までたどる。
実行時に動的に読み込まれるエントリーポイントとして使われるカタログは、動的な製品 API である。
ドキュメントの一覧に載っているだけのものは、呼び出し元に数えない。
第三者に公開されている拡張の経路は、リポジトリ内の呼び出し箇所がゼロでも、意図的なものでありうる。
未使用コードの静的解析を実行するときは、マニフェストに基づく読み込み、生成された出力、コンパイラが参照するエントリーポイントを検査対象に含める。
ワークスペースごとの例外リストを別に持たない。

候補ごとに、現在の所有者、生成側から利用側まで実際に効果を持つ経路、なくなるもの、残るもの、機能と互換性への影響、残すべき最も強い理由を記録する。
候補を次の三つに分ける。

- 到達できない振る舞いや、読まれていない振る舞いの削除。
- 失うものを明示したうえで、公開上または製品上の振る舞いを狭める変更。
- 保護されている義務、または証拠が不十分なもの。

残さなければならない義務を壊す候補、同じ複雑さを別の場所に移すだけの候補、意味のある削減にならない候補は退ける。
過去に退けた理由は、提案された変更の単位で読む。
古くなった一覧や、複数の変更をまとめた提案の中で退けられた項目は、その候補単独についての結論にはならない。
同じ候補を再び提案する前に、証拠を取り直す。
局所的な小さな改善は、独立した設計の記録ではなく、そのまま対応に移れる `TODO` や `FIXME` のコメントにする。

## 所有権と失敗時の意味を保つ

コピー、凍結、検証、コールバックに捕捉された値については、値の出どころ、次の所有者、信頼境界を明示する。
型の付いた同一プロセス内の呼び出しは、通常、読み取り専用の値を借りるだけである。
パーサー、設定ローダー、キュー、モデルやツールとやり取りする JSON、永続ファイル、ワーカー、プロセス、通信データのデコーダーは、入力データを所有するか検証する。
悪意のあるゲッターやコールバックの差し替えを試すテストがあるというだけでは、それらを防ぐ要件があることにはならない。
ルートが凍結されていても、その子孫が不変であるとは限らない。
ID が等しくても、同じオブジェクトであるとは限らない。

非同期の仕組みでは、プロミス、フラグ、キャンセルの経路、破棄の処理、予約のそれぞれを、所有者と状態遷移に対応づける。
仕組みを一つにまとめるのは、それらが同じ事実を表している場合だけにする。
同期的な公開とロールバック、コールバックの封じ込め、最初に確定した結果を採用する調停、ワーカーとプロセスの所有権の管理、完全に停止するまで待つ破棄は、必要とされている箇所では保つ。
永続化された開始と終了の印は、描画で無視されていても、実際に起きた事実を記録していることがある。
中断された作業の記録をなくすことは、冗長なログの整理ではなく機能の喪失である。

## 基盤を置き換えるときの基準

プロジェクトに依存関係の方針があれば、それに従う。
パッケージを追加する前に、既存の依存関係と、サポートする最小バージョンで使える標準ライブラリを調べる。
置き換えによって削除できる実装と専用のテスト、置き換え先の保守コストと推移的な依存のコスト、つなぎのコードが保たなければならない残りの振る舞いを、すべて特定する。

置き換えが成り立たなくなる原因になりやすい不一致を、実際に動かして確かめる。
たとえば、プロトコルの途中での切断、キャンセルと終了処理、設定された上限、決定的なテスト用の時計、プラットフォームごとのパッケージング、ソースとビルド済みのエントリーポイントの違いである。
フレーミングを担うライブラリでも、サイズ上限を守らせるために同じフレーミングを作り直す必要があるなら、簡素化にはならない。
受け入れると決めた境界条件での振る舞いの変化は、提案と関連するテストに書く。
依存先の一般的な仕様をテストで証明し直しておきながら、プロジェクト固有のつなぎのコードのテストを省く、ということをしない。

## 記録、統合、検証

文章がスコープに含まれる場合は、`prose-contract` スキルを使う。
コードを言い直しているだけの説明と、本来は別の場所が持つべき説明を取り除く。
その場所に固有の振る舞い、タイミング、所有権、失敗に関する義務は残す。
影響を受ける README、ドキュメントコメント、モデルやユーザーに見えるカタログ、設定、スナップショット、生成ファイルは、変更と一緒に更新する。

規模の大きい提案には、プロジェクトに決定記録の形式があればそれを使う。
なければ、課題、提案、検討した代替案、受け入れ基準、リスクの五つに分けて書く。
利用側についての具体的な証拠、なくなる保守コスト、失う機能、観測できる受け入れ条件を含める。
同じ決定を扱う記録がすでにあれば、それを更新する。
候補の件数を保つためだけに、重複した記録を作らない。

新しい記録を書くときは、それが既存の記録を置き換えるものかどうかを、関係する範囲で確認する。
コードの調査を依頼されても、リポジトリ全体の記録を監査することにはならない。
一部だけが置き換えられた記録と、永続化、通信形式、互換性、退けた代替案に関して現在も有効な義務は残す。

別のブランチの提案を取り込むときは、そのブランチ独自の差分を、取り込み先のベースと比べる。
証拠の裏付けがあって重複しない提案だけを移し、重複する根拠は一つにまとめる。
他人の PR を閉じるには、許可か、その整理が自分の担当であるという明確な根拠が必要である。

変更した範囲に応じて、プロジェクトのチェックを実行する。
調査した領域、証拠の裏付けがある候補、意味のある却下や見送り、追加、統合、保持、削除した記録、実際に実行したコマンドを報告する。
網羅性を確かめていない検索結果を、網羅的だと書かない。
