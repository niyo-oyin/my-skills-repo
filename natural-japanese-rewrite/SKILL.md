# 自然な日本語へのファイル書き換えスキル

日本語ネイティブの編集者の視点で文章を読んでください。元の意味を損なわず、TPOにふさわしい自然な表現に修正してください。

作業はチャット上だけで完結させず、必ず以下のファイル操作ワークフローに従って進めてください。

## 準備・ファイル命名規則

- 作業ログの保存先ディレクトリは `.agents/rewrite/` とします（存在しない場合は作成してください）。
- 1回の実行ごとに共通のプレフィックス `<YYYY-MM-DD>-<6文字のランダム英数字またはファイル名>`（例: `2026-11-13-a1b2c3`）を発行し、以下の2つのファイルを作成します。
  1. 検査ファイル: `.agents/rewrite/<prefix>-inspect.md`
  2. 検証ファイル: `.agents/rewrite/<prefix>-verify.md`

---

## 最も忌避すべき文体

英語圏のテック系ブログ（Substack や Medium など）や Apple のプレゼンに見られる、短く言い切って含みを持たせる文体があります。英語の *"With every access request, it cuts uncertainty."* のように、カンマで一拍置いてから言い切るのが特徴です。これを日本語にそのまま移した「アクセス要求のたびに、不確実性を削る。」のような書き方を、このスキルでは最も避けるべきものとして扱います。下の「対象外」に当たる場合を除き、すべて直してください。

この文体は文法も意味も正しく、一度読めば内容が分かります。そのため、読んで引っかかった箇所を挙げる方法では見つかりません。内容ではなく形を見て判定してください。

### 現れやすい場所

見出し、箇条書きの先頭に置かれた項目名、表の見出し、キャプション、太字だけの一行、段落の最初と最後の短い文、一文だけの段落。

### 目印

1. **拍を取るための読点**
   短い文の中で、助詞や接続の直後（「を、」「は、」「に、」「で、」「して、」）に打たれた読点のうち、取り除いても係り受けが変わらないもの。日本語の見出しや項目名には、多くの場合読点を打ちません。見出しや項目名にある読点は、列挙の読点（「導入、設定、運用」）を除いてこれに当たります。本文では、主題の「は、」のあとなどに読点を打つのは普通の書き方なので、読点だけを理由に該当とはしません。
   - 「義務を、容認に反転させる」
   - 「数値を残して、計測という出どころを落とす」

2. **二つの項を対にした言い切り**
   抽象的な二つの項を、転換や対比の関係に置いて一文で言い切る型。「AをBに変える」「Aを残してBを落とす」「Aではなく、B」「Aから、Bへ」。
   - 「仮定の話を、出荷済みの機能に格上げする」
   - 「機能ではなく、体験を届ける」

   「設定を初期値に戻す」のように、具体的な操作を述べているだけのものは当たりません。

3. **英語の動詞の比喩をそのまま移した言い方**
   抽象的な名詞に、物を扱う動詞を当てた組み合わせ。その場面の日本語の文章で一般的に使われる組み合わせかどうかで判断します。
   - 「不確実性を削る」「出どころを落とす」「複雑さを手放す」「可能性を解き放つ」

4. **主張を一文で言い切る見出し**
   見出しが、その節の題目ではなく、主張を一文で言い切っている。句点で終わる見出しや、問いかけの見出しも含みます。
   主張を述べる見出しは日本語の文章でも使われることがあるので、これだけでは該当としません。他の目印に当たった見出しについて、判定を補強する材料として記録してください。直す対象は形であり、主張そのものではありません。
   手順書の「環境を構築する」のような見出しは操作の名前なので当たりません。

5. **短い言い切りの連続と、間を作るだけの文**
   「速い。軽い。壊れない。」のように短い言い切りを続けて並べる書き方や、「答えは、シンプルだ。」「問題はそこではない。」のように、中身を言う前に間を作るだけの文。ダッシュ（「——」）やコロンで間を置いてから言い切る書き方も含みます。

6. **文体の切り替わり**
   敬体（です・ます）の文章の中に、常体の言い切りが一文だけ混じっている。
   - 「答えは、シンプルだ。17件のうち12件は、原文が3,000字を超えていました。」の一文目

### 判定

- **見出し、項目名、キャプション**: 目印1か5に当たれば、それだけで該当とします。目印2と3は、両方に当たれば該当、片方だけなら、同じ文書の他の見出しと比べて、その見出しだけ形や語の調子が違うかどうかで決めてください。目印4だけに当たる見出しは非該当です。
- **本文**: 目印5か6に当たれば該当とします。目印1〜3は、二つ以上に当たれば該当、一つだけなら非該当です。「ミスの出方は、原文の渡し方によって変わりました。」のように読点があるだけの文は、短くても該当としません。目印3だけに当たる言い方は、Phase 1 の「語」で扱ってください。
- 一つ見つかったら、同じ階層の見出しと前後の文をすべて見直してください。この文体は同じ型で並んで現れます。

### 対象外

- 広告、スローガン、スライドの表紙、文芸的な文章のように、言い切りのリズムそのものが求められている場面。
- 引用、固有名、コードやコマンドの中の文字列。

### 直し方

直すのは形だけです。原文の用語と、見出しや文が述べている内容は、それが主張であってもそのまま残してください。

見出しは、次の順に必要なところまで手を入れます。

1. 読点を取ります。取ると読みにくくなる場合は、語順や助詞を変えて、読点なしで読める形にしてください。見出しの末尾の句点も取ります。短い言い切りの連続を一つにまとめるときなど、列挙の読点は使ってかまいません（「待たせず、迷わせず、間違えない」）。
2. 「です・ます」で終わる見出しは、名詞句に直します。名詞句にすると元の述語が表している内容が失われる場合に限り、常体の文にとどめてください。
3. 比喩の動詞を、起きていることをそのまま言う動詞に替えます。
4. 同じ階層の他の見出しと形が揃っていなければ、揃えられるかを検討します。体言止めが並んでいれば体言止めに、「〜する」が並んでいれば「〜する」にします。ただし、元の述語が表している内容（何がどうなるか、因果や変化の向き）を残したまま言い換えられる場合に限ります。内容が失われる場合や不自然になる場合は、形が揃わなくても3までにとどめてください。

| 元 | 直した例 | 避ける例 |
| --- | --- | --- |
| 義務を、容認に反転させる | 義務を容認に変える / 義務から容認への反転 | |
| 仮定の話を、出荷済みの機能に格上げする | 仮定の話を出荷済みの機能として扱う | |
| 数値を残して、計測という出どころを落とす | 数値を残して計測値であることを省く | 数値の出どころ（「数値を残して」が消える） |
| 品質は、工程で決まる | 品質は工程で決まる | 品質と工程の関係（「工程で決まる」という主張が消える） |
| 応答時間は、キャッシュの有無によって変わる | キャッシュの有無による応答時間の変化 / 応答時間はキャッシュの有無で変わる | |

本文の短い文は、次のように直します。

- 読点を取り、比喩の動詞を替えます。「アクセス要求のたびに、不確実性を削る。」は「アクセス要求ごとに不確実な点を減らす。」になります。
- 間を作るだけの文は、次の文とつなげます。
- 短い言い切りの連続は、一つの文にまとめます。
- 敬体の文章に混じった常体の言い切りは、敬体に直します。

## 検索して点検する語

意味が通じるので、通読では見逃しやすい語です。「話し言葉の比喩」と「直訳の語」の二種類があります。どちらも対象ファイルから検索し、見つかった箇所を一つずつ判定してください。

### 話し言葉の比喩

口頭の議論で使う感覚的な比喩の語を、書き言葉の文書にそのまま持ち込んだ言い方です。次の一覧の語が対象です。

| 語 | 起きていることをそのまま言う語の例 |
| --- | --- |
| 効く、効いてくる | 効果がある、役に立つ、影響する |
| 落ちる、落とす、落とし込む | 抜ける、失われる、省く、反映する |
| 拾う | 検出する、集める、見つける |
| 倒す（安全側に倒す） | 〜を優先して決める、〜寄りに設定する |
| 潰す | 解消する、取り除く |
| 握る | 合意する |
| 刺さる | 関心を引く、評価される |
| 肝 | 重要な点 |
| 筋が良い、筋が悪い | 妥当だ、適切だ、適切でない |
| 素直に | そのまま、単純に |
| 地味に、地味だが | 目立たないが |
| 解像度 | 理解の細かさ、詳しさ |
| 手触り | 感触、実感 |

検索には次の正規表現が使えます。

`効[かきくけい]|落[ちとし]|拾[わいうえっ]|倒[さしすせ]|潰[さしすせ]|握[らりるれっ]|刺さ[らりるれっ]|肝|筋が|素直|地味|解像度|手触り`

#### 判定

右の列のような語に置き換えても文の意味が変わらなければ、該当とします。

文字どおりの意味で使われている場合と、その分野で定着した組み合わせは非該当です。「キャッシュが効く」「ブレーキが効く」「応答時間が落ちる」「サーバーが落ちる」「テストが落ちる」「画像の解像度」などがこれに当たります。

一覧にない語でも、同じ種類の言い方だと判断したものは挙げてください。

#### 直し方

起きていることをそのまま言う語に置き換えます。置き換える語は文脈から選び、原文にない評価や事実を足さないでください。

| 元 | 直した例 |
| --- | --- |
| この分け方が効きます | この分け方に効果があります |
| 要約で条件が落ちる | 要約で条件が抜ける |
| 肝になるのは有効期限です | 重要なのは有効期限です |
| エラーはログで拾います | エラーはログで検出します |

### 直訳の語

英語の用語に硬い漢語を当てた訳語です。日本語の文書では、その意味では普通使われません。対象は「正本」です。

「正本」は、source of truth や canonical の訳語として使われます（「設定は config.yaml が正本です」）。日本語の「正本」は、法律や事務の場面で文書の種類を指す語です（「契約書の正本と副本」「判決正本」）。

#### 判定

「正本」は、見つかった箇所を原則としてすべて該当とします。非該当は次の場合だけです。

- 法律や事務の用語として、文書の種類を指している場合
- 引用と固有名

#### 直し方

別の一語には置き換えず、その文が述べている内容をそのまま書きます。「正本」が表している内容は、多くの場合、次のどちらかです。

- 内容が食い違ったときに、どれを優先するか
- どれが元のデータで、どれがそこから作られたものか

どちらであるかは文脈から読み取ってください。読み取れない場合は「基準」「元の〜」のような語を使い、原文にない事実を足さないでください。

| 元 | 直した例 |
| --- | --- |
| 設定は config.yaml が正本です | 設定は config.yaml の内容を正とします |
| README と食い違う場合は仕様書が正本です | README と食い違う場合は仕様書を優先します |
| 正本は Figma で、画像は書き出したものです | 元のデータは Figma にあり、画像はそこから書き出したものです |
| このシートを正本として管理します | このシートを基準として管理します |

## 実行ワークフロー

### Phase 1: 場面の推定と違和感の抽出 (Inspect)

対象ファイルを読み込み、以下の1〜5を行って `.agents/rewrite/<prefix>-inspect.md` を作成してください（まだ対象ファイル自体は書き換えないでください）。

1. **場面の推定**
   誰が、どの立場から、誰に向けて、どこで出す文章かを推定し、一行で書いてください。

2. **違和感の抽出**
   その場面に照らして、日本語ネイティブの編集者として読み、引っかかった箇所を次の観点で挙げてください。引っかかる箇所がない観点は「なし」としてください。
   - **語**: 文法的には正しいが実際にはあまり使われない言い方や、場面に合わない硬さや軽さ。
   - **文**: 一度で意味が理解できず読み返した文や、直訳調の表現。
   - **段落**: 読み終えてどれが一番大事な事実か分からなかった段落。
   - **視点**: 主語や語り口が、1で推定した書き手の立場と合っていない箇所。
   - **その他**: 上記以外で、場面に照らして違和感を覚えた箇所。

3. **忌避すべき文体の点検**
   2とは別の作業として、上の「最も忌避すべき文体」に当たる箇所を、形だけを見て洗い出してください。2で引っかからなかった箇所も対象です。
   1. 対象ファイルの見出しをすべて書き出します。Markdown の `#` 行、HTML の見出し要素、太字だけの行、箇条書きの先頭に置かれた項目名、表の見出し、キャプションが対象です。件数が多くても省略しないでください。
   2. 書き出した見出しを一つずつ「目印」と照らし、該当か非該当かと、当てはまった目印の番号を記録します。読点を含む見出しは検索でも見つけられます（Markdown なら正規表現 `^#+ .*、`）。
   3. 本文を通読し、「判定」の本文の基準で該当する文を挙げます。

4. **検索して点検する語の点検**
   上の「検索して点検する語」にある語を、対象ファイルの全体から検索してください。見つかった箇所をすべて書き出し、一つずつ該当か非該当かを判定します。通読して気づいたものだけを挙げる方法は取らないでください。

5. **通し番号**
   2〜4で挙げた箇所に、ファイル全体で通しの番号（`#1`、`#2`、…）を付けてください。同じ箇所が複数の観点に当たる場合は、最初に挙げたところで番号を付け、ほかの観点ではその番号を引くだけにします。この番号の一覧が、Phase 3 で一つずつ確かめるチェックリストになります。

#### `inspect.md` の出力フォーマット
```markdown
# Inspect: [対象ファイルのパス]

## 1. 場面の推定
[一行で記述]

## 2. 引っかかった箇所
### 語
- [通し番号、該当箇所の引用、引っかかった理由 / なし]

### 文
- [通し番号、該当箇所の引用、引っかかった理由 / なし]

### 段落
- [通し番号、該当箇所の引用、引っかかった理由 / なし]

### 視点
- [通し番号、該当箇所の引用、引っかかった理由 / なし]

### その他
- [通し番号、該当箇所の引用、引っかかった理由 / なし]

## 3. 忌避すべき文体の点検
### 見出し（全件）
| 通し番号 | 見出し | 判定 | 当てはまった目印 |
| --- | --- | --- | --- |
| [該当のみ付ける] | [見出しの引用] | [該当 / 非該当 / 対象外] | [目印の番号 / なし] |

### 本文の短い文
- [通し番号、該当箇所の引用、当てはまった目印の番号 / なし]

## 4. 検索して点検する語の点検
| 通し番号 | 語 | その語を含む文 | 判定 |
| --- | --- | --- | --- |
| [該当のみ付ける] | [検索した語] | [検索で見つかった文の引用] | [該当 / 非該当とその理由] |
```

---

### Phase 2: 対象ファイルの書き換え (Rewrite)

作成した `inspect.md` で挙げた箇所を、**対象ファイル上で直接直してください。**

- 語の問題は語を置き換え、文の問題はその文を、段落の問題はその段落を組み直してください。
- 忌避すべき文体に該当した箇所は、「最も忌避すべき文体」の「直し方」に従って直してください。
- 話し言葉の比喩に該当した箇所は、「話し言葉の比喩」の「直し方」に従って直してください。
- 直訳の語に該当した箇所は、「直訳の語」の「直し方」に従って直してください。
- 見出しを書き換えた場合は、その見出しを参照している目次やリンクも合わせて直してください。
- Phase 2 以降は `inspect.md` を変更しないでください。作業中に新しく気づいた箇所は、直したうえで `verify.md` の再修正ログに書きます。
- **それ以外の箇所は元のままにしてください。**

#### 編集ルール（厳守）
- 書き手がどう評価しているかは原文からしか分からないため、**原文にない事実、評価、感情、結論は足さないでください。**
- **原文にある事実と数字も削らないでください。** ただし、正確な数字を残していれば、概数を添えても構いません。
- 変えてよいのは、**主語の選び方、文の切り方とつなぎ方、読点の有無、文末の形（体言止めにするか動詞で終えるか）、段落の分け方、それらの順序**です。
- 大事な事実は、**書く位置と文の切り方**で目立たせてください。

---

### Phase 3: 検証と再修正 (Verify)

書き換えた対象ファイルと原文の差分（`git diff` 等、または編集前後の内容）を比較し、以下を確かめてください。

1. 原文の事実と数字がすべて残っているか。
2. 原文にない事実、評価、感情、結論が加わっていないか。
3. `inspect.md` で通し番号を付けた箇所が、一つ残らず直っているか。また、番号のない箇所を書き換えていないか（見出しの変更に伴う目次やリンクの修正は除く）。番号を一つずつ、書き換え後の該当箇所と対照してください。
4. 忌避すべき文体が残っていないか。書き換え後のファイルの見出しを、Phase 1 の3と同じ手順ですべて点検し直してください。自分が書き換えた文に、この文体が新しく入り込んでいないかも確かめてください。「検索して点検する語」の語も、書き換え後のファイルで検索し直してください。
5. 書き換えた見出しのそれぞれについて、元の見出しが述べていた内容（主張、因果や変化の向き）が、書き換え後の見出しにも残っているか。同じ内容が本文に残っていても、見出しから消えていれば問題として扱ってください。

**違いや問題があれば、必ず対象ファイルを直してから**、最終的な検証結果を `.agents/rewrite/<prefix>-verify.md` に出力してください。

#### `verify.md` の出力フォーマット
