# 契約を残してそれ以外を削る文章の基準

契約を保つために必要な情報を書き、推論の書き起こし、繰り返し、装飾を取り除く。
ここでいう契約とは、呼び出し側、呼び出される側、実装者、生成側、利用側のいずれかが頼りにしている義務、不変条件、事前条件、事後条件、互換性の約束のことである。
コメントでは、コードから読み取れる事実を言い直さない。
コードだけでは表現できない、自明でない契約や理由だけを書く。

これは指針であり、手順書ではない。
原則はどの言語にも当てはまるが、例は日本語で示す。
対象の文章の言語は変えない。

セッションの漏れ（変更の経緯、レビューのやり取り、手元にしかない設計メモの引用など、作業セッションの視点で書かれた文章）を探して直す作業は、`trim-session-leakage` スキルが扱う。

「契約」「境界」「責務」「サーフェス」「ゲート」「語彙」のような抽象語は、禁止語としてではなく、使う前に確かめる語として扱う。
まず、具体的な規則、API、フィールドの集合、型、検証、タイミング、コンポーネントの分け方、失敗を書いたほうが、事実をより正確に述べられないかを問う。
その語が技術上の対象そのもの（呼び出し側と呼び出される側の契約、セキュリティ境界、プロセス境界など）を指している場合は、そのまま使う。

## 入力と除外

スコープ（対象のファイル、ディレクトリ、差分）が明示されていることを確認する。
明示されていなければ、必要な入力が欠けていると報告して止まる。
リポジトリ全体がスコープだと推測しない。

既定では、質問をせずに進める。
対話しながら進めるのは、ユーザーが質問や判断基準のすり合わせを明示的に求めた場合だけである。

質問するかどうかの判断と、書き換える権限は分けて考える。
レビューや監査の依頼では、編集せずに指摘を報告する。
書く、直す、削ることを明示的に求める依頼では、明確な変更を適用する。

ベンダリングされたサードパーティのコード（`vendor/`、`node_modules/` など）は、依頼されたスコープがリポジトリ全体であっても、探索、レビュー、編集の対象から除外する。
シンボリックリンクをたどってその中に入ることもしない。
検索では、除外指定を包含の glob のあとに置き、あとに続く包含指定で除外したものが対象に戻らないようにする（たとえば `rg … --glob '!vendor/**'`、Git では `:(exclude)vendor/**`）。
スコープにサードパーティのコードしか含まれていない場合は、対象になるファイルが残っていないと報告する。

凍結された記録（アーカイブ済みの決定記録、公開済みのリリースノートなど）は書き換えない。
過去の引用が何を意味していたのかを理解するために読むのはよいが、その文章やリンクを現状に合わせて更新してはならない。

生成された出力、スナップショット、フィクスチャは、派生物として扱う。
編集する前に、利用側をすべてたどる。
ソースのドキュメントコメントが、生成されるカタログの元になっていることがある。
先に、それを所有するソースかシナリオを直し、そのあとで派生物をすべて再生成する。
生成器が所有者の文章から要約を抜き出す場合は、抜き出される文を、出力先でそれだけで完結するように書く。

## 命題をすべて残す

編集する前に、その箇所に含まれる命題をすべて特定する。
次の事柄についての記述は、すべて残す。

- 動作の主体と動作
- 条件、タイミング、順序
- 「しなければならない」「してもよい」「決してしない」といった義務や許可の別（モダリティ）
- 起きないことの保証と例外
- 所有権、副作用、失敗の起き方、結果

形容詞、繰り返し、過程の語りを取り除くのは、事実についての記述がすべて残り、結果が前より明確になる場合だけである。
語数が減るだけでは、改善にならない。

使う場所には、それだけで完結した契約を置く。
呼び出し側や保守する人がその場所で必要とする振る舞い、失敗、所有権、結果は、そこに書く。
アーキテクチャ、理由、アルゴリズム、経緯、長い例はそこに書かず、それらを所有する文書に積極的にリンクする。
一つの説明の置き場所は一か所にする。
ただし、契約として欠かせない事実は、使う場所で繰り返してよい。

自明でない理由は、省くと誤用や誤った簡素化を招きそうな場合に残す。
そうでなければ、結果だけを書き、理由はそれを所有する文書にリンクする。

## 操作についての記述は実行して確かめる

ドキュメントは、製品の現在の振る舞いを述べるものである。
コマンド、設定例、既定値、エラーメッセージ、プラットフォームによる違いについての記述で、証拠として認められるのは、実際に実行した結果だけである。

- それぞれの操作を、ドキュメントに載せるとおりの形で、現在のチェックアウトに対して実行する。
  出力、警告、失敗を含め、観測したことだけを書く。
- 再現できなかったものは削除する。
  コマンド、フィールド、既定値、振る舞いを、記憶、類推、隣のパッケージの README から持ち込んではならない。
  記述が再現しないときは、記述のほうを直す。
- 手元にないキーやネットワークのために確認できない場合は、その振る舞いを断定しない。
  未確認であることと、誰が確認すべきかを書く。
- 既存のドキュメントを改訂するときは、古い文章ではなく、最新のコードと照らし合わせる。
  以前の README、議論、報告を、現在のコードとテストより強い証拠として扱わない。

## 文章の場所ごとに必要な内容

この節は、短くするためだけのものではない。
次に挙げる契約が、コード、型、構造から伝わらない場合は、説明を足すか復元する。
その場のコードから明らかな事実には、コメントを足さない。

- **公開 API のドキュメントコメント：** 呼び出し側から見える戻り値の区別、例外や非同期の reject、副作用、所有権、タイミング、キャンセル、永続性を書く。
- **内部のコメント：** 離れた場所にまたがる構造と、見るからに複雑な局所的な構造について、読み手に見通しを与える。
  不変条件、競合時の順序、所有権、セキュリティ境界、意外な失敗時の振る舞いがその対象である。
  制御フローの語りと、コードの言い直しは削除する。
- **モジュールのコメント：** モジュールの役割、依存関係、責務、自明でない設計上の選択を書く。
  設計上の選択は、それぞれを説明する文書にリンクする。
- **テスト：** 自明でないテスト設計だけを説明する。
  そのフィクスチャ、アサーション、プラットフォームへの対応、実際のエントリーポイント、間接的な観測がなぜ必要なのかを書く。
  処理を順に追う説明と、項目の列挙は削除する。
- **クックブック：** 前提条件、必要な操作、実際のエントリーポイント、観測できる検証、簡潔な警告を含める。
- **README：** 利用側との契約を含める。
  設定、意味、失敗、制限、拡張点、モデルに見える影響を書く。
  そのパッケージが所有する安定した文面（プロンプト、結果、エラー）は引用する。
  生成されたカタログと、ほかのパッケージが所有する内容にはリンクする。
  長く続く制限と、保守する人が陥りやすい罠は残す。
  日常的な整理作業は列挙しない。
- **スキルとエージェント向けの指示：** 振る舞いのガードレールと、「これは指針であり、手順書ではない」のような明示的なスコープの限定を書く。
  ワークフローは簡潔に保ち、その出典にリンクする。
- **例と設定のコメント：** アクセスの制限、自明でない配線や読み込み順、セキュリティ上の立場、例外、起こりやすい誤用を説明する。
  設定がすでに示している項目は説明しない。
- **プロンプトと表示される文言：** 文言を振る舞いとして扱う。
  表示テキスト、アクセシビリティ名、ツールチップ、プレースホルダー、書式テンプレートをまとめて調べる。
  モデルやユーザーが目にする文面を変えるときは、その文面を固定しているテストやスナップショットも更新する。
  許可されたスコープにそのテストやシナリオが含まれていない場合は、文言を変えずに、見送りとして報告する。
  文章だけの編集に、黙って紛れ込ませない。
- **診断メッセージ：** 失敗した対象やパス、違反した規則、自明でない場合は直し方を示す。
  内部の実行過程の語りは取り除く。

検索できる仕組みの名前は残す。
モダリティ、時、否定を示す、意味のある強調も残す。
整えるのは、装飾としての強調だけである。

## 読み手の視点で確かめる

リポジトリの文脈を持たないエンジニアが、リンクでつながった 3 から 5 ページを読んだあとで、次の六つの問いに答えられるかを確かめる。
六つの問いとは、その製品や機能が何をするか、どうすれば安全に実行できるか、状態がどこにあるか、どのコンポーネントが所有しているか、どのように失敗するか、どこを変更すればよいかである。
公開されている流れを知るためだけに読み手がソースを読まなければならないなら、欠けている説明を復元する。
読み手が無関係な内部の詳細を読み通さなければならないなら、その詳細をより深い場所に移す。

## ワークフロー

1. スコープ、質問が必要かどうか、現在のブランチまたは PR のベースブランチ、適用される `AGENTS.md` や `CLAUDE.md` を確認する。
  無関係なブランチは調べない。
2. ある箇所を判断する前に、それを所有するコードか文書を読む。
  プロジェクトにドキュメントの規約があれば、先に読む。
  判断基準を確かめたいときや、なじみのないケースでは、[例](references/examples.md)を読む。
3. 大きなファイルだけでなく、依頼されたスコープの全体を調べる。
  検索と語数で候補を見つけ、意味で判断する。
4. 候補を、残す、足す、削る、復元する、組み直す、見送るのいずれかに分類する。
  明確な変更を適用するのは、依頼が編集を許可している場合だけである。
  削除の目標を達成するために、不要な編集をしない。
5. 派生物より先に、所有者を更新する。
  新しい規則が分かったら、似た箇所を確認し直す。
6. 関係する範囲の狭いチェックを実行する。
  プロジェクトのドキュメントのチェックと `git diff --check` を実行し、表示される文言を変えた場合は振る舞いのテストも実行する。
  最終的な差分に、スコープ外のパスが含まれていないことを確認する。
  誤って手を入れてしまった場合は、除外できたと主張せず、そのとおりに報告する。
7. 調べたスコープ、適用した変更、意図的に残したもの、見送ったケース、実際に実行したチェックを報告する。

## 境界線上のケース

次の三つがすべて成り立つ場合に限り、境界線上のケースとする。
命題を残すという規則を満たす版が二つ以上あること、それらの版の間で、認められた原則どうしがトレードオフになっていること、このスキルがそのトレードオフをまだ解決していないことである。
命題を残せる版が一つしかない書き換えは、境界線上のケースではない。

質問をせずに進める場合は、許可された明確な編集を適用し、本当に境界線上にあるケースを、質問はせずに報告する。
先に進めるために命題を弱めない。

対話しながら進める場合は、似た箇所を、それらに当てはまる原則ごとにまとめる。
成り立つ版を二つか三つ示し、そのうちの一つを推薦して、事実や構造の違いを述べる。
劣る版で選択肢を水増ししない。
やり取りは、ユーザーが指定した場所で行う。
PR のインラインコメントで判断基準をすり合わせるときは、推薦する暫定の版を差分に入れ、代替の版をその行に添える。

ユーザーが決めたら、依頼されたスコープの中の似た箇所すべてに、その原則を適用する。
その原則と各版を[例](references/examples.md)に追加することも提案する。
追加するときは、PR の経緯とレビューのやり取りを省く。
