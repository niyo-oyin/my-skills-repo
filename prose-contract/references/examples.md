# 例：削りすぎ、適切、書きすぎ

これらの例は、文章のひな形としてではなく、それぞれの判断の背後にある原則を見分けるために使う。
「適切」とは、欠かせない命題をすべて残したうえで、その場所に必要な説明を最小限にした版のことである。

## 事実を述べる節をすべて残す

**元の文：** 「コーディネーターは、セッションごとに書き込みを注意深く直列化し、破棄が完了する前にバッファ内のイベントを書き出し、バックエンドの失敗を呼び出し側に報告する。」

**削りすぎ：** 「コーディネーターは永続化を直列化する。」

**適切：** 「コーディネーターは、セッションごとに書き込みを直列化し、破棄が完了する前にバッファ内のイベントを書き出し、バックエンドの失敗を呼び出し側に報告する。」

取り除くのは装飾と繰り返しであり、命題ではない。
動作の主体、セッションごとという範囲、破棄との順序関係、失敗が呼び出し側に見えることは、それぞれ別の事実である。

## スキルの明示的なスコープは機能の一部である

**削りすぎ：** 「出典を読み、判断して進める。」

**適切：** 「このスキルは指針であり、完全なチェックリストではない。挙げてある確認項目のほかにも、自分で判断する。文書化された要件は引き続き適用される。」

**書きすぎ：** 一覧が自律的な推論の代わりにならない理由を、数段落にわたって弁護する文章。

スコープの限定は、エージェントがワークフローをどう適用するかを変えるので残す。
削るのは繰り返しの説得であり、ガードレールではない。

## クックブックには操作と検証を残す

**削りすぎ：** 「ツールのテストを追加する。」

**適切：** 「登録と破棄をユニットレベルでテストし、実際のローダーの経路を通してツールを動かし、描画される出力が変わる場合はスナップショットを追加する。アサーションが、モデルの報告ではなく外部の結果を観測していることを確認する。」

**書きすぎ：** 例のコードを見れば分かるフィクスチャとアサーションを、一つずつ順に追う説明。

テストの階層、必要な操作、実際のエントリーポイント、観測できる検証を残す。
フィクスチャの語りは取り除く。

## 所有権とタイミングを残す

**削りすぎ：** 「プロバイダーの処理は、終了処理の中でキャンセルされる。」

**適切：** 「ランタイムは、子スコープを解放する前に、プロバイダーにキャンセルを要求する。破棄が完了する前にワーカーの終了を待つ責任は、引き続きプロバイダーにある。」

**書きすぎ：** 終了処理の実装に使われるプロミスとコールバックを、時系列ですべて説明する文章。

動作の主体、順序、所有権が移る時点、完了の保証は、それぞれ別の事実である。

## イベントのドキュメントコメントには順序を残す

**削りすぎ：** 「保存前のフックを呼び出す。」

**適切：** 「検証に成功したあと、書き込みの前に、保存前のフックをちょうど 1 回呼び出す。フックの中で行った変更は、今回の書き込みに含まれる。フックが例外を投げた場合、書き込みは行われない。」

**書きすぎ：** その順序を実装しているヘルパー関数、キャッシュのフィールド、プロミスのコールバックを順に追う説明。

イベントの順序と、それが現在の操作に及ぼす結果は、呼び出し側から見える振る舞いであり、実装の語りではない。

## 複雑なコードは語らずに見通しを与える

**削りすぎ：** 「ワーカーレルムのサポート。」

**適切：** 「ワーカーレルムと、そのホストブリッジを所有する。レルムの初期化は 1 回だけ行われる。破棄するとワーカーが終了し、以後の呼び出しは reject される。プロトコルの理由については、ワーカー分離の設計文書を参照。」

**書きすぎ：** このあとに続くクラスとヘルパー関数を、段落ごとに予告する文章。

モジュールの役割、依存関係、責務、自明でないライフサイクルの振る舞いを残す。
設計の理由はリンクで示し、局所的な制御フローはコードそのものに語らせる。

## 公開 API のドキュメントコメントには失敗を含める

**削りすぎ：** 「レルムのグローバルを返す。」

**適切：** 「初期化済みのレルムのグローバルを返す。初期化が完了していない場合、またはレルムがすでに破棄されている場合は、例外を投げる。」

**書きすぎ：** それぞれの例外に至る、内部のステートマシンの分岐とヘルパー呼び出しの正確な説明。

例外と、状態についての事前条件は、呼び出し側から見える契約の一部である。

## 実装の対応づけは簡潔に残す

**削りすぎ：** 「外部 API を使う検索プロバイダー。」

**適切：** 「プロバイダーの結果を、共有の検索結果のフィールドに対応づける。タイトル、URL、本文は残し、プロバイダー固有の順位づけのメタデータは捨てる。」

**書きすぎ：** 名前が同じで代入が自明なフィールドまで含めて、対応づけのコードをフィールドごとに言い直す文章。

アダプターがどこで情報を捨て、どこで変えているのかが分かる対応づけの詳細を残す。

## 理由にリンクしてもその場の契約は残す

**削りすぎ：** 「破棄については、ライフサイクルの設計文書に記載がある。」

**適切：** 「破棄すると、実行を中断し、プロバイダーの処理がすべて止まるまで待つ。所有権と競合の扱いについては、ライフサイクルの設計文書を参照。」

**書きすぎ：** 設計文書にあるプロミスの連携の詳細と、退けた所有権のモデルを、すべての破棄処理のそばにコピーする。

振る舞いと完了の保証は、呼び出し側がそれを必要とする場所に残す。
アルゴリズムと理由には、積極的にリンクする。
それでも、リンクはその場の契約の代わりにはならない。

## セキュリティ境界には具体例が一つ必要なことがある

**削りすぎ：** 「読み込まれたプラグインは、ホストの権限を共有する。」

**適切：** 「読み込まれたプラグインは、ホストの権限を共有する。たとえば、シェル実行 API を使えるプラグインは、ホストを実行しているユーザーの権限でコマンドを実行できる。」

**書きすぎ：** プラグインが悪用しうるサービスと、考えられる攻撃をすべて並べた一覧。

例が一つあれば抽象的なセキュリティ上の制限が運用の場面で分かるようになるのなら、その一つを残す。

## 推論の書き起こしは丸ごと削除する

**書きすぎ：** 「まず、ループは値が存在しないかどうかを確認する。存在しなければ、次の分岐で早期に return する。存在すれば先に進むので、最後のアサーションは安全である。」

**適切：** コードがその分岐をすでに表している場合は、コメントを書かない。
早期の return が自明でない不変条件を守っている場合は、その不変条件だけを書く。

推論の書き起こしは、短い語りに圧縮するのではなく、取り除く。

## 設定のコメントでは設定から分からないことを説明する

**書きすぎ：** 「この項目は認証ミドルウェアを読み込み、続いてレート制限、その次にルーティングを読み込む。」
その順序は、並んでいる項目からすでに分かる。

**適切：** 「認証をレート制限より先に読み込み、制限が IP アドレス単位ではなくユーザー単位で適用されるようにする。」

順序がもたらす結果、意外なスコープの規則、セキュリティ境界を残す。
どの項目があるかは、設定そのものに示させる。

## 語数だけを理由に削らない

**現在の文：** 「アダプターは、プロバイダーのエラーを共有のエラー型に変換する。これにより、呼び出し側は、認証の失敗、レート制限、一時的な失敗を同じ方法で扱える。」

**短いが悪くなった文：** 「アダプターは、プロバイダーのエラーを正規化する。」

**適切な判断：** 失敗の種類がリンク先か周囲の契約にすでに挙げられているのでなければ、現在の文を残す。
短い版では、構造が良くなるわけでもないのに、変換の結果と、失敗の種類の区別がなくなる。

## モデルに見える文面は所有者のところで正確に保つ

**削りすぎ：** 「呼び出しに失敗すると、ツールはエラーを返す。」

**書きすぎ：** ほかのパッケージのスキーマと表示文字列を、このパッケージの README にコピーする。

**適切：** このパッケージが所有する安定したプロンプト、結果、エラーの文面を引用する。
スキーマについては生成されたカタログに、ほかのパッケージが所有する文面についてはそのパッケージの README にリンクする。
その場には、このパッケージに固有の条件や差分だけを書く。

モデルに届く文言は振る舞いの一部だが、複製はいずれ食い違う。
正確な文言は、所有者のところに置く。

文章だけを対象にした監査で、疑わしい文言を指摘するのはよい。
しかし、その文言を固定するテストやスナップショットがない場合に、黙って文言を変えてはならない。
文言は変えずに、見送りとして報告する。
変えるには、それを所有するシナリオと必要な証拠を含めて、変更の許可を得る。

## 抜き出される要約は単独で成り立たせる

**削りすぎ：** 「承認リクエストとポリシーのサービス。」
所有者は、ポリシーの順序と監査ログについて後続の文で説明しているが、カタログが抜き出すのは最初の文だけである。

**書きすぎ：** サービスのライフサイクル全体と通知の振る舞いを、抜き出される一文に詰め込む。

**適切：** 「回答者より先にセッションのポリシーを適用し、すべてのリクエストと結果の組を、リクエスト元のセッションに記録する承認サービス。」
カタログに載せる必要のない詳細は、後続の文に置く。

生成器が何を抜き出すのかを把握する。
抜き出される部分は、生成された出力の上で必要になる契約を保っていなければならない。

## 制限は契約であり負債の一覧ではない

**削りすぎ：** 設定の変更にプラグインの再読み込みが必要になる原因である、プロセスが生きている間ずっと保持されるキャッシュについて書かない。

**書きすぎ：** 呼び出し側にも保守する人にも影響しない、非公開のヘルパーの整理や、テスト専用の未使用アクセサーを列挙する。

**適切：** 「プロバイダーの選択は、プラグインが生きている間キャッシュされる。プロバイダーをインストールまたは修復したときは、再読み込みが必要である。」
日常的な整理作業は、TODO か issue トラッカーに置く。

利用や安全な保守に影響する欠落と、自明でない制約を残す。
パッケージの README は、バックログの置き場ではない。
