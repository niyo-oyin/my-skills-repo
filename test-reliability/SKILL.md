# CI で信頼できるテスト

ほかに負荷のないローカルマシンで単独で実行したときだけでなく、リポジトリの実際の CI の実行構成（トポロジー）のもとでも正しく動くテストを作る。
このスキルが扱うのは、分離と信頼性についての判断である。
プロジェクトのテスト方針（どの階層のテストを書くか）の代わりにはならず、プッシュの前に実行するコマンドを選ぶものでもない。
これは指針であり、手順書ではない。

## 最初に読むもの

- プロジェクトにテスト方針の文書があれば、それに従って、どの種類の証拠（ユニット、カバレッジ、期待出力、スナップショット、ブラウザ、実 API）が必要かを選ぶ。
- ライフサイクル、子プロセス、キャンセル、後始末についての規約があれば、それに従う。
- ワーカーの数やジョブの構成がテストに影響する場合は、テストランナーの設定と CI のワークフローを読む。

## 実行トポロジーを把握する

次の各層では、実際に適用される設定で否定されていない限り、実行が重なりうると考える。

1. 一つのテストファイルの中のテストどうし。
2. 別々のテストファイル、またはワーカープロセスどうし。
3. 一つのジョブの中で独立に動く、テストランナーやチェックのプロセスどうし。
4. ランナーが一つのホストを共有している、別々の CI ジョブどうし。

プロセスを分離しても、ホストのポート、予測できるファイルパス、外部サービス、データベース、ソケット、引き継がれた子プロセスは分離されない。
確保するリソースの一つひとつについて、次の五つを特定する。
所有者、アトミックに割り当てる仕組み、準備ができたことを示す観測可能なシグナル、登録された後始末、完全に停止したことを示すシグナルである。

一つのフィクスチャが分離できていないというだけの理由で、スイート全体を直列にしない。
先に、排他にする範囲を狭めるか、リソースの割り当て方を変える。
テストランナーの逐次実行ブロックでは、別のファイル、プロセス、ジョブ、ランナーからホストのリソースを守れない。

## リソースをアトミックに確保する

空きを確認してからあとで確保するのではなく、リソースの所有者が提供する割り当ての仕組みを使う。

- ネットワークのフィクスチャは、ループバックのポート 0 にバインドする（Node.js では `listen(0)`）。
  割り当てられたアドレスは、サーバーが待ち受けを始めたと報告してから読む。
  空きポートを探してからあとでバインドする方法は、決して使わない。
- テストごとの専用の一時ディレクトリを、オペレーティングシステムの仕組み（`mkdtemp` など）で作る。
  予測できる共有のパスを確保しない。
- 共有のデータベース、ソケット、セッション、出力先には、テストごとに一意の名前空間を与える。
- パスがすでに存在していてはならない場合は、排他的な作成を使う。
- 記録された安定した識別子と、一時的な通信用のアドレスを分けておく。
  実際のリソースに記録された値を使わせるのではなく、フィクスチャの中で変換する。

パーサーの入力や期待値としてだけ使われるリテラルのパスや URL は、確保されるリソースではない。
固定に見えるというだけの理由で、書き換えない。

## プロセス全体で共有される状態を閉じ込める

環境変数、カレントディレクトリ、偽のタイマー、ロケールとタイムゾーン、モジュールのモック、レジストリ、コンソールのフック、グローバルオブジェクト、HTTP 通信のグローバルな横取りは、排他的に使う可変のリソースとして扱う。

依存を注入する方法か、インスタンスに閉じたアダプターを優先する。
変更が避けられない場合は、次のようにする。

- 元の値が存在しなかったのか、存在したのかを記録しておく。
- その状態を正確に復元する。
- 変更の直後に、復元の処理を登録する。
- 変更の範囲をできるだけ小さくし、`try/finally` で囲む。
- その `finally` に達する前に失敗しうる場合は、テストごとの後処理のフック（`afterEach` など）にも復元の処理を入れる。
- 横取りするのは、フィクスチャが所有する、最も範囲の狭い特定のリクエストや呼び出しだけにする。

## プラットフォームに依存する振る舞い

CI は、同じスイートを Windows と POSIX の両方のホストで実行する。
オペレーティングシステムが管理する値は、テストが書き込んだとおりに読み戻せるとは限らない。

- 値を書き戻す操作が安全なのは、書き戻しに失敗してもアサーションが成り立つ場合だけである。
  ファイルの更新時刻を元に戻したうえで、それでもフィンガープリントが無効になることを示すアサーションは、どの環境でも成り立つ。
  更新時刻を元に戻したうえで、記録が有効なままであることを示すアサーションは、書き戻しても値が変わらないことを前提にしている。
  NTFS はタイムスタンプを 100 ナノ秒単位で保持するので、ミリ秒未満の端数を持つ値は、書き戻すと同じ値にならない。
  アサーションが復元に依存する場合は、覚えておいた値ではなく、読み直した値を期待値にする。
- Windows は、環境変数の名前を大文字と小文字の区別なしで照合する。
  `http_proxy` と `HTTP_PROXY` を別々のキーとして設定するフィクスチャは、Windows では一つの項目しか持たない。
- Windows は、ファイルハンドルを非同期に解放する。
  POSIX のホストではすぐに完了する名前の変更や削除でも、観測された競合の程度に合わせた、回数に上限のある再試行が必要である。
- Windows には、POSIX のパーミッションやシグナルの意味がない。
  それらに依存するテストは、すべてのプラットフォームでアサーションを弱めるのではなく、Windows で理由を示して明示的にスキップする。

どのプラットフォームでも成り立つ観測を使う。
本当にそれができないテストだけを、そのプラットフォームで明示的に除外する。

## タイムアウトを CI の制限時間に合わせて決める

多くのテストランナーでは、個々のスイートやテストに書いたタイムアウトが、ランナー全体の設定より優先される。
そのため、CI ジョブの制限時間より小さい値を書くと、CI がすでに認めていた時間を縮めることになる。
既定値がそれより小さいホストでは、同じ値が逆に時間を延ばすものとして働く。
プロセスの生成に時間を取られるスイートには、ジョブの制限時間を使う。
それより短い値を書くなら、短くする理由を明記する。

テストの制限時間を延ばすときは、フックの制限時間も一緒に延ばす。
準備と後始末も、同じ競合の影響を受ける。
テストの制限時間だけを延ばしても、競合による失敗が後処理のフックに移るだけである。

タイムアウトそのものがテストの対象である場合は、外側の待機時間を、テスト対象のタイムアウトよりずっと長くする。
20 ミリ秒の期限が発火することを証明するテストが、テストハーネス自身の待機と競争してはならない。
競争になると、どちらの期限が先に報告されるかは負荷で決まってしまう。

## 状態を見て同期する

固定時間のスリープは、準備が完了したことの証拠にも、後始末が終わったことの証拠にもならない。

- 準備完了を示す明示的なイベントやハンドシェイク、状態遷移、自分が所有するプロミス、外部から観測できる条件を待つ。
- 遅延プロミスやバリアを使って、競合を決定的な地点に置き、関係する操作が重なることを証明する。
- タイムアウトは、待機に上限を設けるためだけに使う。
  アサーションを成り立たせる条件として使ってはならない。
- スケジューラーに依存する順序をアサートしない。
  その順序がテスト対象の製品の振る舞いである場合は例外とする。
- 時間そのものがテストの対象である場合は、時計を注入するか偽のタイマーを使い、必ず本物のタイマーに戻す。

## 後始末を最後まで完了させる

リソースを確保した直後に、後始末を登録する。
こうしておけば、アサーションが失敗してもリソースが解放される。
後始末では、新しいコールバックとリクエストを止め、リスナーを外し、グローバルなフックを復元し、自分が所有する処理を終了させる。
そのうえで、子プロセスの終了、サーバーのクローズ、ワーカーの終了など、完了を示すシグナルを待つ。

`abort()`、`close()`、`kill()` を呼ぶだけで完了のシグナルを待たない後始末は、不完全である。
後始末のあとで処理が遅れて完了しうる場合は、その処理が別のテストの状態を変えられないことを証明する。

## 意図した退行を立証する

- 現実的に可能なら、通常の回帰テストが修正の前に失敗するところを観測する。
- 新しい静的チェックや、ファイルの集合を対象にしたチェックを追加するときは、拒否されるべきケースを一時的に入れ、意図したとおりに失敗するところを観測する（陰性対照）。
- 競合については、バリアを使って実行が重なることを証明する。
  繰り返し実行するだけでは、競合のテストにならない。
- ポート、ソケット、共有のパス、子プロセスなどのホストのリソースについては、プロセス間の分離が修正の一部である場合、独立したテストプロセスを同時に実行する。
- フィクスチャが独自の期限を持つ子プロセスを起動する場合は、終了ステータスをアサートする前に、シグナルやタイムアウトで子プロセスが終了させられていないことをアサートする。
  こうすると、強制終了された子プロセスが、ステータスの不一致ではなくタイムアウトとして報告される。
- コンポーネントの自己申告を信用せず、外部の状態、イベント、ファイル、ログ、終了、後始末を検証する。

負荷をかけた繰り返しの実行は、決定的な回帰テストを補うものであり、その代わりにはならない。

## フレークを隠すだけの修正を退ける

決定的に動くはずのローカルのテストについて、次のものを根本原因の修正として受け入れない。

- 待っている状態を特定せずに、タイムアウトを延ばす。
- 再試行を足す。
- すべてのファイルを直列にする。
- エラーや、処理されていないプロミスの reject を黙って捨てる。
- アサーションを弱める。
- 不安定な振る舞いを正規化して見えなくする。
- 後始末やアサーションの前にスリープを入れる。

再試行は、稼働中の外部プロバイダーを呼び出すテストで、一時的な失敗の再試行が文書化された方針になっている場合には妥当である。
この例外は、外部との境界に限って適用する。

制限時間を元に戻すことは、フレークを隠すことではない。
スイートのタイムアウトを、もともと与えられていたジョブの制限時間まで延ばすことも、回数に上限のある再試行を、ランナーで実際に計測した競合の程度に合わせることも、何を待っているのかを特定したうえでの対応である。
どちらも、調べていない待機の周りに根拠のない余裕を作るものではない。

## 既存のフレークを診断する

すでに起きている確率的な CI の失敗については、[フレーク診断のワークフロー](references/flake-diagnosis.md)を読む。
診断だけの依頼では、読み取り専用のまま進める。
ユーザーが修正も求めていない限り、原因と証拠だけを報告する。

## 検証と報告

影響を受ける振る舞いについて、最も小さく絞った回帰テストを実行する。
トポロジーに固有の証拠を足すのは、その変更がそのリスクを抱えている場合だけである。

- グローバルな状態の変更には、復元の証拠が必要である。
- ライフサイクルや子プロセスに関わる作業には、完全に停止するまで後始末したことの証拠が必要である。
- ポート、ソケット、共有のパスには、同時に動く独立したプロセスでの証拠が必要である。
- 新しいチェックには、陰性対照が必要である。

実行したコマンドと観測した結果を、正確に報告する。
再試行した作業、スキップしたテスト、結果待ちの CI を、成功したと書かない。
