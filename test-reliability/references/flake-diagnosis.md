# フレーク診断のワークフロー

このワークフローは、すでに起きている確率的なテストや CI の失敗を調べるときにだけ使う。
依頼された読み取りと書き込みの範囲を守る。
診断だけの依頼は、修正、ワークフローの再実行、CI の設定変更を許可するものではない。

## 証拠を固定する

リポジトリ、ワークフロー、ジョブ、コミットの SHA、ランナーのラベル、タイムスタンプ、失敗したテストやコマンドの正確な名前、最初に現れる安定した失敗のシグネチャを記録する。
インフラのメッセージは、テストの出力と分けておく。

失敗した実行と成功した実行をそれぞれ複数集めて、比較する。
同じ SHA の実行を優先する。
それができない場合は、比較するコミットの間で、関係するテストと CI の設定が同一であることを確認する。
再実行が 1 回成功しても、インフラの障害だったことの証明にはならない。
タイムアウトが 1 回起きても、製品に競合があることの証明にはならない。

CI のログとメタデータを使って、失敗が一つのホストや一つのリソースの名前空間で重なっているかどうかを確定させる。
長いログを貼り付けるのではなく、根拠になる実行へのリンクを残す。

## 失敗を分類する

最終的な修正からではなく、記録した証拠から分類する。

- **ホストのリソースの衝突：** 独立したプロセスやジョブが、同じポート、ソケット、データベース、予測できるパス、キャッシュ、外部の名前空間を確保している。
- **不完全なライフサイクル：** 子プロセス、ワーカー、ストリーム、サーバー、コールバックが完全に停止する前に、後始末が呼び出し側に戻っている。
  あとから出た出力やファイルの変更が、別のテストに現れる。
- **プロセス全体で共有される状態の汚染：** 結果が、テストの順序や、漏れ出した環境変数、カレントディレクトリ、偽のタイマー、グローバル、モック、ロケール、モジュールの状態に依存している。
- **負荷に敏感な同期：** スリープ、ポーリングの間隔、イベントループが一巡するという想定が、観測可能な準備完了や完了の代わりに使われている。
- **プラットフォームやエントリーポイントの不一致：** 失敗が、オペレーティングシステム、シェル、ファイルシステムの規則、ソース実行とビルド実行の違い、実行可能なエントリーポイントのいずれかと一貫して結びついている。
  タイムスタンプの精度、環境変数名の大文字と小文字、ハンドルが解放されるタイミング、パーミッションの意味は、Windows と POSIX のホストで異なる。
  そのため、macOS で成功しても、Windows のジョブについては何も分からない。
- **製品の並行性の欠陥：** テスト自身がリソースを管理していて、重なりを明示的に作ると失敗が決定的に再現し、出荷される製品の振る舞いそのものに競合が現れる。
- **外部プロバイダーの一時的な失敗：** 失敗の原因が稼働中の API やネットワークの境界にあり、文書化された再試行の方針に合致している。
- **ランナーのインフラ：** チェックアウト、依存関係のダウンロード、ディスク、ホストのプロセス、ランナーのサービスが、テストのコマンドとは無関係に失敗している。
  この分類には、ランナーについての直接の証拠が必要である。
  ランナーがホストのメトリクスを公開していない場合は、そのことを述べ、ログから分かる事実をもとに分類する。
  ホストを調べられなくても、同じプールの上で、無関係なブランチにまたがって同じシグネチャが繰り返されていれば、共有ホストでの競合の証拠になる。

証拠が複数の独立した事実を裏付けている場合は、それぞれを報告する。
タイムアウト、シグナル、終了コード、アサーションの失敗を、推測した一つの結論にまとめない。

## 関係する最小のトポロジーで再現する

問題のテストファイルか、絞り込んだテスト名から始める。
並行の度合いを上げるのは、シグネチャを再現する最初のトポロジーまでにする。

1. テストプロセス一つ。
2. 同時に動くテスト、または同時に動くファイル。
3. 複数の独立したテストランナーのプロセス。
4. プロジェクトのチェック一式を、設定されたワーカー数で実行したもの。
5. 疑わしいホストのリソースを共有する、別々のジョブやランナーのプロセス。

有効になっているテストランナーの設定、環境変数による調整、ソース実行かビルド実行か、プラットフォームを、失敗した実行に合わせる。
別の失敗を作り出すためだけに、製品が実際に使っているタイムアウトを短くしたり、無作為な負荷を足したりしない。

シグネチャが、手元のホストでは動かせないプラットフォームに固有のものである場合、ローカルでの再現は、到達できる最後の段階で止まる。
別のプラットフォームで成功した実行で代用せず、その限界を記録する。
そのうえで、CI を再現の場として使う。
結果を一つの原因に結びつけられるように、1 回の実行で変える疑わしい箇所は一つだけにする。

競合が疑われる場合は、確率的なタイミングを、争われている状態遷移に置いたバリアに置き換える。
ホストでの衝突が疑われる場合は、同じ識別子が同時に確保されていることを証明する。
あるいは、アトミックで一意な割り当てによって衝突がなくなることを証明する。

## 所有者のところで修正する

実装が許可されている場合は、リソースを割り当てているコンポーネント、準備完了を公開しているコンポーネント、グローバルな状態を変更しているコンポーネント、後始末を所有しているコンポーネントを修正する。
スナップショットの正規化、再試行のラッパー、長くしたタイムアウト、全体を直列にする設定、弱めたアサーションで失敗を隠さない。

安定したフィクスチャのデータは、実際のリソースの割り当てと分けておく。
記録された URL を固定のままにして、実際の通信だけを、フィクスチャが OS の割り当てたポートに対応づけることができる。
固定のパスをアサーションの期待値として残しても、実際の出力先を、共有の書き込み可能なディレクトリにする必要はない。

## 調査を終える

証拠がそろったと言えるのは、次のすべてが成り立つ場合だけである。

- 元のシグネチャに、証拠に裏付けられた分類が付いている。
- 関係する最小のトポロジーで、それが再現する。
  または、外部の証拠が十分にあり、再現の限界が明示されている。
- 許可された修正が、陰性対照のもとで、または修正前の状態で失敗し、修正後は同じトポロジーで成功する。
- リソースの所有者が必要とする証明（同時に動くプロセス、復元、完全に停止するまでの後始末）が通る。
- 残りの CI のチェックが、観測した状態に基づいて、成功、結果待ち、スキップ、失敗のいずれかとして報告されている。

たまたま成功するまでテストを実行して、その結果を安定していると呼ばない。
選んだ証拠で結論が確定したら、そこで止める。
確定しない場合は、どの事実が欠けているために分類できないのかを報告する。
