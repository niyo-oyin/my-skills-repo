# 決定記録（ADR）の参照と記録

決定記録は、何を決めたかと、なぜそう決めたかを残す文書である。
元の会話を読まなくても決定とその理由が分かるように、記録だけで完結させる。
実装計画と検証手順は、決定記録ではなく issue か PR に書く。

このスキルが扱う決定記録は、追記だけで運用する。
承認済みの記録は決定した時点の記録としてそのまま残し、決定を覆すときは新しい記録で置き換える。
記録にあるパス、名前、既定値は、決定した時点のものである。
現在の値は、コードと現行のドキュメントで確認する。

これは指針であり、手順書ではない。

## プロジェクトの規約を優先する

プロジェクトに決定記録の置き場所と形式がすでにあれば、それに従う。
記録は `docs/decisions/`、`docs/adr/`、`doc/adr/`、`adr/` などに置かれていることが多い。
見つからなければ、`AGENTS.md`、`CLAUDE.md`、コントリビューター向けのドキュメントに指示がないかを確認する。

採番の方式、節の構成、状態の表し方、索引の有無は、そのディレクトリの README と既存の記録に合わせる。
承認済みの記録を現状に合わせて書き換える運用のプロジェクトでは、その運用に従う。
[既定の形式](references/format.md)を使うのは、決定記録を新しく導入するときと、プロジェクトの規約が定めていない点を補うときだけである。

## 変更を始める前に

構成、依存関係、インフラ、公開 API、データ形式、運用方針に関わる変更を始める前に、決定記録の一覧を確認し、関係する記録を全文読む。

- 一覧はファイル名で確認し、索引があれば索引でも確認する。
  変更しようとしているものの名前でも検索する。
- 置き換え済みの注記がある記録は、それを置き換えた記録も読む。
- コードに `ADR:` コメントがあれば、その記録を読む。
- 承認済みの決定と、それが課している制約に従う。

これから行う変更が承認済みの決定と矛盾する場合は、実装する前にユーザーに伝える。
ユーザーに伝えずに、別の選択肢に差し替えない。
ユーザーがその決定の変更を明示的に求めた場合は、[決定を置き換える](#決定を置き換える)に従って記録する。

既存の実装が決定と矛盾しているのを見つけた場合も、報告する。
どちらが正しいかを推測で決めない。

決定に沿って実装したときは、PR の説明でその記録に触れる。
理由がコードから読み取りにくい箇所では、主要な入口に 1 行のコメントを置いてもよい。

```typescript
// ADR: docs/decisions/2026-06-15-use-sqlite-for-test-database.md
```

## 記録する決定

次のすべてを満たす決定を記録する。

- システムの作り方か動かし方を変える。
- 現実的な代替案があった。
- 今後の作業に影響する。
- 理由が、コード、テスト、既存のドキュメントから読み取れない。

局所的な実装上の選択、通常のバグ修正、機械的な変更、書式や命名の好みは記録しない。
判断の基準は、実装の大きさではなく決定の重さである。
小さな変更でも、互換性や所有権について長く影響する規則を定めるものは、記録の候補になる。

その決定を扱う記録がすでにあれば、新しく書かずにその記録を参照する。

採用しなかった提案を独立した記録にするのは、その提案が何度も持ち上がりそうな場合だけである。
その場合は、「X をしない」という決定として書く。

作業の途中で記録に値する決定が出てきたら、記録することを提案する。
ユーザーが記録を明示的に求めていない場合は、書く前に確認する。
依頼された範囲を超えて、記録を追加したり変更したりしない。

迷ったときは、[例](references/examples.md#記録するかどうかの判断)を読む。

## 記録を書く

1. [変更を始める前に](#変更を始める前に)に従って既存の記録を読み、同じ決定を扱う記録や矛盾する記録がないかを確認する。
2. 関係するコード、依存関係、制約を調べる。
  渡された議論や依頼から、課題、選んだ案、代替案、受け入れたトレードオフ、対象外の事項を抜き出す。
3. 決定の理由に関わる情報が足りなければ、ユーザーに尋ねる。
  手元の資料から分かることは尋ねない。
4. 次の節で書く。
  完成した例は[例](references/examples.md#完成した記録)にある。

- **背景と課題**：何が問題か、なぜ今決めるのか、どのような制約があるかを書く。
- **決定**：何を選んだか、なぜ選んだか、適用する範囲、対象外の事項、受け入れたトレードオフを書く。
- **検討した代替案**：それぞれの利点と欠点、選ばなかった理由を書く。
- **補足**（任意）：関連する記録、PR、issue、決定を見直す条件を書く。

書くときは、次の点を守る。

- 実際に検討した代替案だけを記録する。
  記録のために作らない。
  何と比べて選んだのかが書かれていない決定は、再検討を招く。
- 過去の決定をあとから記録する場合で、代替案を確認できないときは、「検討した代替案」に、記録が残っていないと書く。
  この節を省くことも、推測で埋めることもしない。
- 一つのトレードオフは一か所に書く。
  選んだ案のトレードオフは「決定」に、ほかの案のトレードオフは「検討した代替案」に書き、別の節で繰り返さない。
- 実装の手順、ファイルごとの変更一覧、検証のチェックリストを書かない。
  それらを持つ issue や PR にリンクする。
- 作業セッションの中にしかない資料を引用しない。
  代替案を、手元の設計メモや、会話の中だけで使った呼び名（「B 案」）で指さず、名前と内容を記録の中に書く。
  決定記録は経緯を書く場所なので、決定に至るまでの経過そのものは書いてよい。
  この区別は、`trim-session-leakage` スキルが扱う。
- テンプレートを埋めるために内容を水増ししない。

## 記録をレビューする

自分が書いた記録と、レビューを依頼された記録を、次の問いで確かめる。

**その場にいなかった人やエージェントが、元の会話を読まずに、何を決めたかと、なぜそう決めたかを理解できるか。**

- 課題と、今それを決めるきっかけが明確か。
- 用語は、内部の事情を知らなくても読めるか。
- 選んだ案とその理由が明記されているか。
- 適用する範囲と対象外の事項が明確か。
- 受け入れたコストとリスクが、決定と一緒に書かれているか。
- 代替案は、実際に検討したものか。
  それぞれを選ばなかった理由が明確か。
- 埋められていないプレースホルダーや、中身のない節が残っていないか。
- 置き換える記録や関連する記録がある場合、リンクされているか。

理由が欠けていれば、ユーザーに尋ねる。
推測で埋めない。
レビューだけを依頼された場合は、指摘の報告にとどめ、編集しない。

## 承認後の記録の扱い

記録は、デフォルトブランチに入った時点で承認済みになる。
それまでは提案であり、自由に書き換えてよい。

承認済みの記録には、次の書き換えをしない。

- 決定、理由、代替案の意味を変える書き換え。
- パス、名前、既定値を現状に合わせる書き換え。

認められる変更は、次の三つである。

- 置き換え済み、または廃止の注記を冒頭に足す。
- あとから分かったことを、日付を付けて「補足」に追記する。
  元の理由は残す。
- 意味を変えない修正をする。
  誤字の修正、記録どうしの切れたリンクの修正、作業セッションの視点で書かれた文章の言い換えがこれに当たる。

承認済みの記録は削除しない。

### 決定を置き換える

決定を覆すとき、または大きく変えるときは、古い記録を書き換えずに新しい記録を書く。

1. 新しい記録の「背景と課題」に、置き換える記録へのリンクと、前回の決定から何が変わったかを書く。
  前回の決定の理由のうち、今も成り立つものと成り立たなくなったものを区別する。
2. 古い記録の冒頭に、新しい記録へのリンクを付けた置き換え済みの注記を足す。
  本文は変更しない。
3. 索引があれば更新し、古い記録を指している `ADR:` コメントを新しい記録に向け直す。

決定の一部だけを置き換える場合は、両方の記録を有効なままにする。
置き換える範囲を新しい記録に書き、置き換えられた範囲を古い記録の注記にも書く。

代わりの決定がないまま決定が適用されなくなった場合（たとえば、対象の機能が削除された場合）は、新しい記録を書かず、古い記録の冒頭に廃止の注記と理由を足す。

注記の書き方と例は、[既定の形式](references/format.md#注記と追記)と[例](references/examples.md#置き換えの例)にある。

## 決定記録を導入する

プロジェクトに決定記録がなく、ユーザーが導入か最初の記録を求めた場合は、次のように進める。

1. 置き場所を決める。
  プロジェクトがドキュメントを置いている方法に従い、規約がなければ `docs/decisions/` を使う。
2. そのディレクトリに、規約を説明する README を置く。
  テンプレートは[既定の形式](references/format.md#readme-のテンプレート)にある。
  記録だけを依頼された場合でも、README を一緒に置くことを提案してから、README を作る。
  リポジトリに規約がないと、次に書かれる記録が同じ形式にならないからである。
3. エージェント向けの指示（`AGENTS.md`、`CLAUDE.md` など）に、置き場所と、変更の前に記録を読むという規則を足すことを提案する。
  このスキルを持たない人やエージェントにも、規約が伝わるようにするためである。

導入も記録も求められていないときに記録に値する決定が出てきた場合は、導入の提案にとどめる。

## 報告

読んだ記録、従った決定、見つけた矛盾、書いた記録、足した注記を報告する。
理由を確認できなかった箇所は、埋めずに、欠けていると報告する。
