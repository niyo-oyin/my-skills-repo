# 例

## 完成した記録

```markdown
# ジョブキューを PostgreSQL のテーブルで実装する

## 背景と課題

レポートの生成とメールの送信は、リクエストの処理の中で同期的に実行されている。
レポートの生成がゲートウェイのタイムアウト（30 秒）を超えることがあり、そのときはユーザーにエラーが返る。
この処理をリクエストから切り離して、非同期に実行する仕組みが必要である。

運用しているデータストアは PostgreSQL だけで、運用の担当者は 1 人である。
ジョブの量は、1 日あたり数千件を見込んでいる。

## 決定

ジョブキューを、既存の PostgreSQL の上に、テーブルと `SELECT … FOR UPDATE SKIP LOCKED` で実装する。
専用のメッセージブローカーは導入しない。

ジョブの投入を、業務データの更新と同じトランザクションで行える。
そのため、更新は成功したのにジョブが投入されていない、という不整合が起こらない。
運用する対象も増えない。

その代わりに、スループットがデータベースの性能で制限されることと、ワーカーのポーリングによって遅延が生じることを受け入れる。

ジョブどうしの実行順序の保証と、複数のサービスへのイベント配信は対象外とする。

## 検討した代替案

- **Redis ベースのキュー**：より高いスループットを扱え、実績のあるライブラリがある。
  しかし、運用するデータストアが一つ増え、ジョブの投入と業務データの更新を同じトランザクションにできない。
- **クラウドのマネージドキュー**：運用の手間が最も少ない。
  しかし、ローカルと CI で動かすにはエミュレーターが必要で、こちらも同じトランザクションにできない。

## 補足

- 実装と検証：#212
- 見直す条件：ジョブが 1 日あたり 100 万件を超える、または複数のサービスからの購読が必要になる。
```

## 記録するかどうかの判断

| 変更 | 判断 | 理由 |
|---|---|---|
| テスト用データベースを、共有の PostgreSQL から SQLite に切り替える | 記録する | システムの動かし方が変わり、代替案があり、以後のテストの書き方を制約する。 |
| 公開 API のエラーレスポンスの形式を決める | 記録する | 利用者に対する互換性の約束になり、あとから変えにくい。 |
| ORM を採用する、または採用しない | 記録する | 依存関係の選択であり、理由がコードから読み取れない。 |
| 繰り返し提案される「設定ファイルを YAML に移す」という案を採用しない | 記録する | 「しない」という決定を残さないと、同じ議論が繰り返される。 |
| ID の型を数値から文字列に変える（数行の変更） | 記録する | 実装は小さいが、保存形式と互換性の規則を定める。 |
| 関数を二つに分ける、変数の名前を変える | 記録しない | 局所的な実装上の選択である。 |
| 依存パッケージのパッチバージョンを上げる | 記録しない | 機械的な変更である。 |
| 境界値の誤りによるバグを修正する | 記録しない | 誤りの訂正であり、決定ではない。 |
| 一度出てすぐに退けられた案を見送る | 記録しない | 関連する決定があれば、その決定の代替案に書けば足りる。 |

## 単独で読めない記録を直す

元の会話の文脈がないと読めない記録は、名前と内容を記録の中に書く形に直す。

**修正前**：

```markdown
## 決定

B 案で進める。
A 案は、性能面の懸念があるので見送る。
```

**修正後**：

```markdown
## 決定

セッションの状態を、サーバーのメモリではなく Redis に保存する。
サーバーを複数台に増やしても、どのサーバーからも同じセッションを読めるようにするためである。

## 検討した代替案

- **署名付きの Cookie に保存する**：サーバー側の保存場所が要らない。
  しかし、状態が 4 KB の上限を超える画面があり、リクエストごとの転送量も増える。
```

修正前の記録には、「性能面の懸念」が何についての懸念なのかが書かれていない。
文書の内容から確認できない場合は、推測で埋めずにユーザーに尋ねる。

## 置き換えの例

古い記録には、冒頭に注記だけを足す。
本文には手を入れない。

```markdown
# テスト用データベースに SQLite を使う

> **置き換え済み**（2026-09-02）：[テスト用データベースに PostgreSQL コンテナを使う](2026-09-02-use-postgres-container-for-test-database.md)

## 背景と課題

…
```

新しい記録では、置き換える記録と、前回の決定のあとに何が変わったかを「背景と課題」に書く。

```markdown
# テスト用データベースに PostgreSQL コンテナを使う

## 背景と課題

[テスト用データベースに SQLite を使う](2026-06-15-use-sqlite-for-test-database.md)を置き換える。

前回の決定では、テストの準備にかかる時間を短くするために SQLite を選んだ。
その後、検索機能が PostgreSQL の全文検索に依存するようになり、検索のテストを SQLite で実行できなくなった。
テストどうしを分離したいという理由は、今も成り立つ。

## 決定

…
```

一部だけを置き換える場合は、古い記録も有効なままにし、置き換えられた範囲を冒頭の注記に書く。

```markdown
> **一部置き換え済み**（2026-09-02）：CI での実行は[CI のテストに PostgreSQL コンテナを使う](2026-09-02-use-postgres-container-in-ci.md)に従う。
```
